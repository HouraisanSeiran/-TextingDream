# 元素装配 · 使用说明

状态：**实现完成，专项测试通过**。作者侧独立页面（左侧导航「◆ 元素装配」），把本地候选素材库里的条目按版本挑进当前故事包，形成开局锁定的元素清单。

- 代码：`app/element_assembly.py`（库访问策略、选择清单、清单构建/校验、公开投影）、`app/static/element-assembly.js`（页面）、`tools/encyclopedia_build.py`（可复现构库 CLI）
- 测试：`tests/test_element_assembly.py`、`tests/test_element_assembly_integration.py`
- 库内容来源：`docs/human-encyclopedia/*.json` 六组 + `docs/element-catalog/*.json` 六组（只读，本功能从不改写它们）

---

## 1. 边界：它做什么，不做什么

| 是 | 不是 |
|---|---|
| 作者选条目 → 固定版本 → 写进 `story.mechanics.element_manifest` 的清单 | 不是「把百科全库装进世界」；每条都要作者显式确认与适配 |
| 锁定后随故事包导出/导入，空机器也能读 | 不是运行期查询库；旅程里不会因为库更新长出新的元素类型 |
| 作者能看到完整原始 payload 与固定来源版本 | 玩家/NPC 只看作者显式写下的公开说明与白名单字段 |
| 显式 typed 规则（依赖 / 互斥）参与机器校验 | 不把条目里的自然语言 `requires` / `excludes` 当机器依赖，也不做「全文语义一致性证明」 |
| 记住库里的 `review_status` / `detail_status` 原值 | 不升格、不改写、不宣称条目已事实核实 |

库里的 481 条都是待审候选（`needs_review` + `needs_detail`）。**采纳只锁定版本，不改变审核状态**；库里存在也不等于事实可信、更不等于世界里已经有。

## 2. 先准备候选库（可复现）

正式库默认在 `artifacts/human-encyclopedia/encyclopedia.sqlite3`，该目录在 `.gitignore` 里，所以新克隆的机器要自己生成一次：

```powershell
D:\anaconda\python.exe -X utf8 -m tools.encyclopedia_build            # 按显式 12 组名单导入
D:\anaconda\python.exe -X utf8 -m tools.encyclopedia_build --check    # 只核对现有库与名单条数
D:\anaconda\python.exe -X utf8 -m tools.encyclopedia_build --out temp/db.sqlite3
```

- 名单是写死的 12 组：`docs/human-encyclopedia/`（staples / produce / flavors / animal-foods / materials / tools）与 `docs/element-catalog/`（eastern / western / society / steam-horror / reality-physical / reality-human）。`shared-themes.json` 是聚类索引、不是元素，故意不在名单里。
- 同一批文件重复导入是**幂等**的（元素级 + 批次级哈希）：第二次运行零写入。
- 源 JSON 只读；本工具从不改写它们。
- **应用启动不会建库、也不会填库**：库里没有内容时页面明确提示运行上面的命令，不做静默兜底。

库位置只由服务端配置决定，页面/接口**不接受路径参数**：

| 变量 | 作用 |
|---|---|
| `TEXTILEDREAM_ENCYCLOPEDIA_DB` | 指定库文件（相对路径按工作区根解析） |
| `TEXTILEDREAM_ENCYCLOPEDIA_ROOTS` | 额外允许的目录（`os.pathsep` 分隔），用于把库放到工作区之外时显式授权 |

解析出的路径必须落在允许目录内，否则拒绝；错误信息里只出现相对路径。测试可用 `Service.elements.configure(路径, allowed_roots=[…])` 显式注入临时库。

## 3. 页面操作流程

1. **检索**：名称/别名子串 + 标签（任一命中）+ 命名空间，分页返回；每行显示 `namespace/element_id v版本` 与两种审核状态。
2. **查看详情**：七节全文、额外分节、适配映射、标签与别名、**每个来源的固定版本**（`source_id v版本` + 标题/URL/access + 支撑范围与权利说明），以及版本历史。来源之后升级时，历史条目仍然显示当初固定的那一版，并标注「来源之后有更新，证据版本不变」。
3. **加入清单**，逐条填：
   - **固定版本**：整数版本号（客户端提交的数字会被服务端按库里的真实版本重新核对）；
   - **状态**：`existing`（世界里已存在）或 `potential`（预绑定但尚未出现，例如「允许研发、但还没有成品」的蒸汽技术）；
   - **公开说明**：作者定稿、玩家可见的那一两句话（≤600 字，超长会被拒绝，不自动截断）；
   - **公开字段**：白名单（七节 + `summary / variants / story_roles / background / entry_modes / introduction_limits / genres / category`），最多 8 个；**列表之外一律拒绝**；
   - **限定地点 / reveal_flag / known_by**：三者都显式，必须同时满足才投影；
   - **潜在元素也允许透露其存在**（`reveal_potential`）：不勾选时，玩家永远不会被告知这个潜在元素存在；
   - **候选确认**：勾上才算确认「这是待审候选、采纳不改变审核状态」，否则提交会被拒绝。
4. **保存草稿** → **校验并试算**（列出清单摘要、逐条警告：自然语言条件、未公开、无受众、未限定地点等）→ **锁定到故事包**。
5. 锁定会在**一次** `commit_package` 里生成新的故事包版本；已有旅程保持旧版本，不受影响。重复提交同一份清单是幂等的（返回「当前故事包已是这份清单」），陈旧基准会被拒绝且零副作用。

提交接口必须同时给出 `expected_draft_revision`（草稿版本）与 `expected_story_revision`（故事包版本），两个都不能省：省了就无法区分「重试」与「拿旧页面改新世界」。草稿在**创建那一刻**就固定了它所属的世界（`base_story_id`）与基准版本（`base_story_revision`）；提交时 `expected_story_revision` 必须**等于这份草稿创建时的基准**，世界前进后旧草稿不会隐式 rebase（需另建草稿），指针换成别的世界也同样拒绝。顺序是：核对世界身份与原始基准 → 查包内提交凭据（receipt）做精确重试 → 构建清单 → **在短事务里预留草稿版本**（构建期间被别人改过就失败，零世界副作用）→ 一次 `commit_package` → 写索引。包里会同时写入一份不可变的 `receipt`（`draft_id` / `base_revision` / `digest`，不参与语义 digest），所以提交成功后即使源库被删除，重试也只核对凭据、不重建清单；幂等重试**不写草稿**（版本号与更新时间不变）。索引写入失败不会被报成「提交失败」（世界已经变了），只会提示「再次提交会幂等补齐索引」。

页面里所有作者文本都用 `textContent` 写入，不会被当成标记。

### 中断恢复

若进程在预留之后直接退出（没走失败分支），草稿会停在 `committing`。恢复是显式且安全的：应用启动时（包事务日志恢复之后）自动跑一次，作者也可以在页面点「恢复中断的提交」（`POST /api/inner/elements/recover`）。规则：

* 只处理**不是本进程**持有的预留（用进程启动 token 区分），不靠现实时间超时抢别的进程；本进程正在进行的提交不受影响。
* 若当前同世界故事包的 `receipt` 证明这份草稿确实已提交 → 补齐索引（不会重复建版本）。
* 否则把草稿放回可编辑状态，但 `revision` **不回退**（单调递增，避免旧版本号又能写入）；作者刷新后继续编辑。
* 本版本**不宣称**支持多进程同时编辑故事包，也不参与故事包目录的搬迁（那由包事务日志处理）。

## 4. 清单结构（`story.mechanics.element_manifest`，version 1）

```
{version, locked_at,
 library {schema_version, path, namespaces},
 count,
 elements [{ref: "namespace/element_id", namespace, element_id, version, content_hash,
            schema_kind, adapter, name, aliases, tags, summary,
            review_status, detail_status,          ← 只记录库里的原值
            state: existing | potential,
            payload {…完整原始对象…}, payload_hash, payload_chars,
            details {七节}, details_map,
            sources [{source_id, source_namespace, source_version, payload_hash,
                      payload {…完整来源记录，含 supports / rights_note…}}],
            relations [...],
            disclosure {public_description, public_fields[], public_text{},
                        location_id, reveal_flag, known_by[], reveal_potential, note},
            adaptation {note, constraints[]},
            warnings[], unsupported[]}],
 rules {version, items [{kind: requires|conflicts, from, to, from_version?, to_version?}]},
 receipt {draft_id, base_revision, digest, committed_at, warnings},
 warnings[], unsupported[], note}
```

- `payload_hash = sha256(canonical(payload))`：导入/校验时重算比对，手改过的清单会被拒绝。
- 来源固定的是**完整来源记录 + 版本号 + 哈希**，不是只有标题链接；库被删除或来源升级都不影响已锁定的证据。
- 上限：16 个元素 / 单元素 payload 30 000 字符 / 整份清单 200 000 字符 / 64 条规则 / 单元素 16 个来源 / 公开字段 8 × 600 字符。16 条是 V1 的安全边界，**不是「一个世界只能有 16 个元素」的世界观结论**。

## 5. 显式 typed 规则（唯一会被机器校验的依赖）

| 规则 | 含义 | 校验 |
|---|---|---|
| `requires` | 选了 `from` 就必须也选了 `to` | 两端都必须在清单内（缺引用报错）；有环报错并给出路径；规则里写的版本必须与所选版本一致 |
| `conflicts` | 两者不能同时存在 | 两端都被选中 → 报错；只有一端在本清单里 → 作为「守卫」记录并警告（将来加入时会被拒绝）；两端都不在 → 报错（不知道它约束什么） |

条目里的 `requires / excludes / background / entry_modes / introduction_limits / story_roles / evidence_note` 是**自然语言条件**：本版本只把它们写进 `warnings` 逐条提示，不做解析、不做推断，也不假装已校验。条目里若出现 `rule_refs / mechanics / effects / rewards / scripts / formula`，记为 `unsupported`：**不把百科条目编译成可执行规则、奖励模板或法术**。

## 6. 公开 / 秘密投影

- 作者视图：完整 payload、来源证据、审核原值、全部警告。
- 玩家与 NPC 视图：**只读 `disclosure`，永不读 payload**——没有「字段名带 secret 就安全」这种猜测。
- 投影条件（全部必须满足）：`known_by` 非空且含该受众；有 `location_id` 时必须是该受众当前所在地点；有 `reveal_flag` 时该标记必须已置位；`potential` 元素必须显式 `reveal_potential`。
- `known_by` 留空 = 谁都看不到（不是「所有人」）。提交时会警告「公开内容没有受众」。
- 进入叙事上下文的 `current_elements` 是**有界**的：最多 6 条、整段 ≤3000 字符；超出时**整条丢弃**而不是截断句子（截断会把「不能」变成「能」）。上下文里不带完整详情、来源或审核标记。
- 作者写下的公开说明就是这个世界的设定：告诉模型「必须服从当前旅程状态、不等于已经发生或已被执行」，而不是把审核标记当剧情传闻灌给玩家。

## 7. 生成与城镇联动

- **世界生成器 / 分阶段流水线**：创建草稿时固定清单（缺省取当前故事包快照；请求里的 `elements` 只能引用**该清单内**的 `namespace/element_id`（可带 `@版本`），越界会被拒绝）。选中元素声明的 `requires` 会按清单里**已固定的精确版本自动补全**（含传递依赖）；依赖目标不在清单里时直接拒绝，展开后若同时出现互斥两端也拒绝——**不会用「删掉规则 + 只留警告」的方式通过硬依赖**。`conflicts` 守卫（另一端不在子集）原样保留。完整清单随生成结果进入编译后的故事包，保存/启用不丢。作者侧上下文只给有界摘要，并标注「候选资料 / 设计输入，不是已核实事实」。
- **新世界重排 ID**：把清单带到新世界时，解析不了的公开地点/受众会被**清空**并记警告（谁都看不到），绝不沿用非法 ID，也不会因为「想让它还能看到」而放宽范围；作者需要重新指定公开范围。
- **城镇生成**：故事包有清单时，`TownInput.bindings` 只能用清单里的精确 ID + 版本，声明的状态必须与清单一致。`potential` 元素的绑定只作为预绑定记录，**不视为已启用的技术、材料或资源**（不会因为百科里有「蒸汽机」就自动解锁锅炉或燃料）。没有清单的老包行为完全不变。

---

## 8. 已知限制（如实）

1. 库只读、审核状态不变：本功能没有任何升格路径。
2. 不做事实核验，也不做跨条目「语义一致性证明」。
3. 不做自动规则转换：没有任何把条目变成奖励/法术/生产配方的映射（首版明确未实现）。
4. 不做经营、势力或经济 tick，不接外部地形工具。
5. 检索是词法匹配（名称/别名子串 + 标签），没有向量检索与拼音。
6. 清单上限（16/30 000/200 000）是工程安全边界，不等于内容上限判断。
7. 运行期 `current_elements` 只给公开摘要；完整设定仍在故事包里，需要时由作者侧查询。
8. 库被删除后仍能读旧旅程，但**无法再装配新清单**（会明确报「百科库不存在，请运行构库命令」）。
