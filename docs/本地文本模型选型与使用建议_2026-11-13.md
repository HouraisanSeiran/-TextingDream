# 本地文本模型选型与使用建议

核对日期：2026-11-13。用途：为织梦选择本地文本模型，分别评估 RTX 2080 SUPER 8 GB、纯 CPU，以及 CPU 与显卡共同运行。本文是选型与后续验证建议；本轮未下载权重、启动推理、训练模型或修改正式配置。显卡当前暂不可用，恢复前只安排资料核对与 CPU 方案。输出预算后续已集中统一，见[模型输出规范](模型输出规范.md)；真实对话验证见[本地模型对话测试](本地模型对话测试.md)。

## 1. 当前建议

**专家模型先比较 LFM2.5-8B-A1B 和 Granite-4.0-H-Tiny；中文叙述同时保留 Qwen3-4B-Instruct-2507 与 Qwen3.5-4B 作为对照。** Qwen3.5-9B 可以放在显卡恢复后的第二轮。现有 Qwen3-4B 继续作为已验证连接的基准，不因新模型参数或榜单更好就直接替换。

| 使用条件 | 优先比较 | 理由与限制 |
|---|---|---|
| 纯 CPU，Ryzen 7 7735HS | LFM3-1.7B 小模型对照；LFM2.5-8B-A1B、Granite-4.0-H-Tiny 专家对照；Qwen3-4B-Instruct-2507 中文对照 | LFM3 权重更小但不是 MoE；两个 MoE 每 token 只用一部分专家。速度与中文质量需要在本机分别测量 |
| 2080 SUPER 8 GB 恢复后 | Qwen3-4B-Instruct-2507、Qwen3.5-4B，加上述两个小型 MoE | 权重有机会连同短上下文一起放进显存；“有机会”不代表已经验证所有缓存和算子都能运行 |
| 更注重质量、允许更慢 | Qwen3.5-9B Q4_K_M | 量化权重约 5.29 GiB，8 GB 显存剩余空间较少，先试短上下文、单请求；纯 CPU 也可测试但不作为默认交互选择 |
| CPU 与显卡共同运行 | 上述小模型先测；30B／35B MoE 暂缓 | 部分权重可放主存，但本机约 15.2 GiB 总内存，Windows、地图服务和生成器也要使用，不宜把大专家模型当稳妥默认 |

这不是所有已发布模型的完整排名。候选以本次实际读到的发布方模型卡、配置和文件清单为依据；发布方榜单只用于筛选，不能代替织梦中文故事任务的比较。

- 显卡：此前只读查询为 RTX 2080 SUPER，8192 MiB；本轮按用户要求继续以这张卡评估，当前不运行显卡任务。
- 已有模型：`D:/llm/qwen3/models/Qwen3-4B-Q4_K_M.gguf` 约 2.33 GiB、`Qwen3-8B-Q4_K_M.gguf` 约 4.68 GiB，以及 0.6B／1.7B Base 和若干研究用 LoRA。Base、指令模型、适配器分别看待。
- 已有运行程序：`D:/llm/qwen3/runtime/llama-server.exe`，本轮 `--version` 返回 build 11349、commit `fb4b2737a`。新版模型能被最新框架支持，不表示这个已安装版本必然支持，加载前需核对。

## 3. “只调用部分参数”意味着什么

稀疏专家模型（MoE）在一部分网络层中有多个专家，由模型内部的路由器为每个 token 选用其中几个。它主要节省该 token 的计算，**不表示只需下载或保存这些激活参数**。共享层、词嵌入和其他结构仍需运行；不同 token 还可能选择不同专家。

例如 LFM2.5-8B-A1B 实际是约 83 亿总参数、15 亿激活参数，不能把名称中的 A1B 当作精确的十亿。Granite 的总参数与激活参数也分别记录。见[专家候选核对](本地专家模型候选核对_2026-11-13.md)。

通常需要保存整份量化权重。CPU 内存映射、磁盘分页和专家缓存可以改变驻留方式，但频繁从 SSD 换入专家可能明显增加等待，不能按“激活了多少”估算响应速度。放在 CPU 的专家也不会因为其他层在显卡上就自动免去计算和传输成本。

专家不是天然的“文学专家”“种族专家”。不能直接指定只用某个专家写故事、随意删掉其他专家，或通过降低选中专家数获得等价质量；这类改动需要专门训练和验证。

**不要把混合注意力等同于 MoE。** Qwen3.5 小模型卡的系列介绍提到稀疏专家，但 4B／9B 各自配置是 `qwen3_5_text` 和普通 `intermediate_size`；35B-A3B 才是 `qwen3_5_moe_text`，有 `num_experts` 等字段。这里按具体配置区分。[S3][S5][S13]

旧 LFM2-8B-A1B 的模型卡已经指向 LFM2.5；本轮优先考察新版。发布方模型卡后续版本链接可能继续变化，不把一次查询当作全球最新型号保证。

### 性能依据怎么读

Qwen3-4B-Instruct-2507 官方模型卡同表报告：旧 4B 非思考与 2507 的 IFEval 为 81.2／83.4，Creative Writing v3 为 53.6／83.5，WritingBench 为 68.5／83.4。[S1] 这些是发布方测试，未证明同一 GGUF 量化后仍维持相同差距，也未直接衡量本项目的中文人物一致性。

旧 LFM2 官方速度比较使用 Ryzen AI 9 HX 370、特定量化和内部 XNNPACK／自定义 MoE 内核；不能据此给本机 7735HS＋llama.cpp 填相同的 token/s。LFM2.5 卡也有性能与 CPU 图表，本轮没有将图表数值当作本机测速。

## 5. 2080 SUPER 8 GB 方案

1. **短请求加载与连接测试先用 Q4_K_M、单请求、4096 总上下文**。这不是默认背景生成全流程的运行配置。总上下文包括输入与输出；当前地图摘要和背景阶段较大，需按实际任务分批，不能给 4096 输入再额外要求长输出。完整任务的建议见第7节。
2. 新模型分别验证所有层放显卡与部分层放显卡的情况，记录实际显存峰值和主存。约 4～5 GiB 权重不等于还可任意扩大上下文；MoE 共享结构、注意力缓存、混合模型的状态和计算缓冲区均占空间。
3. 2080 SUPER 属于 Turing 路线。不要把在 Ampere／更新架构、BF16／FP8／FP4 或 FlashAttention 特定内核上的结果直接套用；现有 llama.cpp CUDA 量化路线可作为起点，新架构的算子兼容仍需实际加载验证。
4. 现有程序帮助中有 `--cpu-moe` 与 `--n-cpu-moe`：可以把全部或前若干层专家权重留在 CPU，其他部分由显卡运行。这是分配方式，不是内存自动减少或必然提速。具体模型、Windows 构建和运行参数要一起验证。

当前显卡不可用，不执行上述验证，也不把旧测试称作新模型已通过。

## 6. 纯 CPU 方案

以现有 Qwen3-4B 先建立对照，再测新小型 MoE。起始设置建议：8 个生成线程、8 个输入处理线程、单请求、4096 总上下文、128～256 输出 token。线程数再比较 4／8／16，不能把16逻辑线程直接当作最快设置。

未来测试时，现有模型的起始命令可写为：

```powershell
& 'D:/llm/qwen3/runtime/llama-server.exe' `
  --model 'D:/llm/qwen3/models/Qwen3-4B-Q4_K_M.gguf' `
  --host 127.0.0.1 --port 18083 `
  --device none --n-gpu-layers 0 `
  --ctx-size 4096 --parallel 1 `
  --threads 8 --threads-batch 8 `
  --chat-template-kwargs '{"enable_thinking":false}'
```

本轮未执行。端口使用前检查是否空闲；命令仅用于现有 Qwen3 的起始对照，新模型需用自己的聊天模板和思考设置。恢复显卡方案应另开独立验证，不能把此命令的 CPU 结果混入显卡测试。

纯 CPU 的主要不确定性是内存带宽、输入长度和解码速度。内存映射可减少启动复制，但不能让 17 GiB 模型在约 15.2 GiB 主存中获得与完全驻留同等的速度。先测4～5 GiB以内的模型，避免为大型 MoE 长时间分页而失去交互性。

## 7. 如何用于织梦

### 接口与任务

沿用[模型接入说明](model-connection.md)及现有 [Provider](../app/provider.py)、[协议适配](../app/ai_protocols.py)。本机服务需支持 `/v1/models`、`/v1/chat/completions`、纯文本正文，以及作者任务使用的 `response_format: {"type":"json_object"}`。本地免密地址已受支持。

| 任务 | 建议使用方式 | 仍由工程决定的内容 |
|---|---|---|
| 玩家短叙述与人物回应 | 本地小模型生成短段落；只读取角色可知资料 | 检定、钱物、时间、已确认后果和秘密可见性 |
| 玩家意图匹配 | 模型在已有合法动作中选择，无法匹配时返回空选项 | 动作是否合法、条件和实际执行 |
| 世界历史与国家背景 | 按任务分批提供地图摘要、采用资料和模拟事实；先生成草稿 | 来源、版本、历史骨架和作者审核发布 |
| 资料整理 | 辅助提取、改写和格式整理 | 原始来源的真实性、引用存在及审核状态 |

工程现有 `dialogue_model`／`author_model` 只是在**同一个请求地址和凭据**下按任务选择模型名，不等于已经支持“作者走远端、玩家走本机”两套独立服务。若将来需要这种分工，应单独补服务路由；本轮不声称已经实现。

### 思考模式和输出

- Qwen3-4B-Instruct-2507 是非思考模型，不要求输入旧版的关闭思考开关。[S1]
- Qwen3.5 默认思考；官方要求通过服务参数关闭，说明不支持沿用 Qwen3 的文字软开关。工程某些提示词里有 `/no_think`，不能据此认定新版已经关闭。需在服务端正确设置模板或补明确参数适配，测试时检查最终正文及结构化输出。[S3]
- LFM、Granite 使用各自模板，不能统一套 Qwen 模板。思考输出和最终 JSON 混在一起会导致现有解析失败；具体行为在部署验收时核对。
- 4K 是起始工程测试条件，不是模型官方最大能力。关闭思考、缩短输出、减少输入，属于低等待时间方案；与官方长输出、高预算测评结果分别理解。

### 本工程对上下文长度的实际要求

**作者生成需要比短对话更大的上下文，但目前没有要求必须使用 128K／256K 的设计。4K 不能直接覆盖默认生成流程。** 下表是后续部署的测试起点，不是已经测得的最低配置或成功保证；K 按约 1024 token 理解，均指单次请求的总窗口。

| 任务 | 建议测试起点 | 当前代码依据与限制 |
|---|---|---|
| 意图匹配、短现场叙述 | 4K，输入较多时升到 8K | [现场判定](../app/scene_judgment.py)分别限制输出为256、1024 token；人物资料、合法动作及现场条件仍占输入，不能保证所有场景都能放入4K |
| 带近期历史、人物和知识的游玩请求 | 8K～16K | 按请求实际输入量核对，不把每个故事包完整送入模型；复杂场景可能需要裁剪或更大窗口 |
| 世界背景生成 | 16K 起测，32K 作较宽裕的对照 | [背景流程](../app/background_package.py)已经分批读取环境、采用资料及历史；环境、资料、历史阶段输出上限统一为8192 token，国家、大陆和总概为4096。16K 下仍可能需要缩小批次或输出预算 |
| 旧城镇／分阶段世界生成 | 16K～32K，并按阶段检查 | [旧分阶段生成器](../app/world_pipeline.py)默认输出上限为8192 token，并携带已完成阶段的数据、结构要求和示例；输入会随阶段增加 |

[偏好设置](../app/contracts.py)默认 `context_chars=18000`，可配置范围为 6000～40000。**这是输入字符预算，不是 token 数，也不是模型服务的实际窗口。** 中文、英文、JSON 字段和引用使用不同分词方式，不能固定按一个比例换算。背景流程的输入检查及分批主要依据此字符预算，尚未按具体模型分词并统一为输出预留空间。

一般应满足：**实际输入 token ＋ 输出预算 ＋ 消息模板等开销，不超过服务实际配置的上下文窗口。** 有思考过程时也要计入模型及服务对应的生成预算。模型标称支持128K，不表示本机服务已经配置128K；[请求层](../app/provider.py)目前也不会自动读取服务窗口并调整批次。旧API设置中的 `max_tokens` 默认8192，作为未登记任务的输出后备值；已登记任务使用集中默认值，显式请求优先，不能把它解释成总上下文或所有任务的统一上限。

地图数组通过统计摘要输入；采用资料和史事分批处理；游玩知识按需检索。世界规模扩大因此不必等比例扩大单次窗口。分批也存在合并后的输入预算和跨批一致性问题，长窗口不能代替来源保存、引用检查和审核。

对本机的建议是：CPU先以短请求测速度，再用8K／16K实际任务评估输入处理时间和峰值内存；2080 SUPER恢复后，优先用4B量化模型测同样的窗口。32K只是作者任务的容量对照，是否适配8 GB显存须按模型缓存、缓冲区及并发实测。MoE节省激活计算，不自动降低长上下文缓存需求；混合注意力或状态模型则需按具体结构评估。

本日后续已实现[分任务输出上限](模型输出规范.md)。若要让小窗口稳定覆盖全流程，仍需补按模型计数的输入预算，并让分批为输出留足空间；不能只把服务设为4K、其余设置保持默认。输入分词与自动分批预留仍是待实施改进，未运行模型。

## 8. 微调、LoRA 与 CNN 的位置

先比较未经本项目训练的指令模型。对齐是目标，监督微调是训练方式，LoRA／QLoRA 是节省训练资源的做法，可以组合使用。已有研究适配器训练的是编程与研究行为，不直接当作游戏叙述能力提升；本地小实验只证明流程可运行，没有证明提升。

训练内容优先来自实测错误：结果档位不一致、人物越过知情范围、制度与个人态度混同、JSON 不合规、名称和文风不稳定。变化中的地图、国家与世界历史继续按故事包提供，不把微调当作更新资料库的替代方案。新架构尤其 MoE 的8 GB微调可行性，要按具体层、上下文、优化器和训练库重新测量；不能从旧4B QLoRA成功推导全部候选都可训练。显卡不可用期间不安排这类训练。

CNN 适合处理局部栅格、地形和空间模式；已经有明确字段时先直接计算。文字表达优先用文本模型，结构化条件评分先比较规则或简单模型。现有检定先由规则结算，再让文本模型描述，见[检定说明](check-system-v2.md)。如果希望新增耗时、暴露、伤害或信息完整度等结果维度，需先定义数据和后果，不能靠模型写得更细自动获得可靠机制。

### 连续对话风险、记忆与专项微调

2026-11-13补充：本地小模型可能在数轮后遗漏约定、人物口吻趋同、只回应最后一句、无条件迎合玩家、混淆传闻与事实、反转检定结果或重复措辞。“注意力涣散”只是表现，不能直接等同于模型随运行时间疲劳；每轮实际提供的资料、模型利用资料的能力、模板及生成设置都要核对。

当前[短现场叙述](../app/scene_judgment.py)只传最近3轮原始对话、玩家最近少量已知信息及人物各自最近少量信念，再补可公开人物卡和本轮结果；没有直接复用普通对话全部记忆组织。普通对话则经[运行时](../app/runtime.py)和[阶段历史](../app/context_stage.py)提供阶段内历史、有限摘录及检索，仍受预算裁剪。3轮不代表整个工程的统一记忆长度，也不能由“存档完整”推导“每轮请求包含完整存档”。

| 表现 | 优先核对 | 处理方向 |
|---|---|---|
| 忘记早期条件或承诺 | 该条件是否进入本次请求，是否有来源及知情人 | 先保存并检索重要事项；微调不能恢复没有提供的信息 |
| 资料在输入里却反复忽略 | 条件位置、提示负担、模型基础能力 | 精简任务，比较候选，再收集错误做多轮监督微调 |
| 人物趋同、过度讨好 | 人物目标、利益、底线是否明确，是否带入当前关系 | 用角色差异、协商与拒绝样本做行为对齐 |
| 泄露秘密或把猜测当事实 | 输入是否越过可见边界；模型是否混淆来源 | 先按人物隔离资料，再训练知情与不确定表达 |
| 失败写成成功、凭空成交 | 已结算结果是否清楚；叙述是否遵从 | 保留规则结算与结构校验，训练忠实表达结果 |
| 复读或答非所问 | 近期历史、采样、模板、思考模式和候选质量 | 用相同材料逐项对照，不先认定必须扩大窗口或训练 |

建议顺序是：**重要事项记忆与两条对话路径核对 → 输入精简与基线测试 → 错误分类 → 多轮监督微调／LoRA → 未见场景回归**。重要事项应区分当前话题、双方目标、已确认条件、未决问题、承诺、拒绝及其来源和知情人；这是待实施方向，尚未新增统一的对话事项存储，不把人物不同信念合并成全员共同知识。

对齐是目标，监督微调是训练方法，LoRA／QLoRA是节省训练资源的实现方式，可以一起使用。第一轮训练围绕人物底线、知情边界、连续协商、传闻表达、遵守已结算结果与输出格式，使用多轮样本。仅单问单答训练难以检验长期承诺和话题延续。监督微调后若仍有明确的行为偏好问题，再考虑成对偏好训练；不将其当作第一步必需项。

训练与验收必须留出未参与训练的人物、故事包和较长对话，同样测试基础模型、改进记忆后的模型及微调模型，分别衡量提升。不要把错误模型回复直接批量作为正确答案；发生变化的地图、旅程事实与人物私有秘密仍按故事包及存档提供，不能靠权重更新管理。LoRA不会自动减小推理所需总窗口或替代外部记忆。

2080 SUPER 8 GB上的4B量化LoRA只列作后续实验候选，需按训练长度、实现和内存实测。显卡当前不可用，先准备数据规范、错误清单和[连续对话验收](本地模型对话测试.md)，本轮没有开始训练、扩大历史窗口或修改记忆机制。

## 9. 后续验证与决定标准

显卡恢复前先准备测试材料和 CPU 对照；恢复后用同一批输入再测显卡。每次记录模型来源／精确版本、量化文件哈希、运行程序版本、硬件、模板、思考设置、上下文、输出预算和并发。

| 要验证什么 | 怎么记录 |
|---|---|
| 等待时间 | 区分冷启动、输入处理、首 token 和完整回答；输入长度与输出长度分别统计 |
| 输出速度 | 解码 token/s、实际输出 token、是否提前结束；同时记录最终可用中文字数及耗时，跨分词器不只比较 token/s；不把两次短请求折算为稳定速度 |
| 内存与显存 | 系统可用内存、进程峰值、显存峰值、是否换页或退到 CPU |
| 规则一致性 | 成败与档位是否反转、是否多发物品／钱物／秘密、是否添加未确认史事 |
| 结构输出 | JSON可解析、字段合法、引用真实存在、空选项与缺值是否正确 |
| 中文叙述 | 人物差异、称谓、冗余、复读、第一印象和制度条件是否表达正确；由作者盲评 |

选定后先用于一类任务，再扩大范围。若 MoE 更快但中文文风较弱，可用于意图匹配或资料提取；若 Qwen 更符合叙述要求，则保留其叙述职责。是否分开模型，取决于实际任务结果和服务能力。

本轮只完成资料核对、选型和接口检查：**没有新候选的本机 token/s，没有新候选8 GB显卡加载结论，也没有自动升级运行程序或切换正式模型。**

### 多轮数据规范

以JSONL保存会话样本，每行包含一个可独立审阅的会话或目标轮次。可复用现有可玩包及其临时旅程，不要求新建剧情包。至少保留下列字段，训练程序只取需要的消息字段，其余用来审核和评估。

| 字段 | 内容与用途 |
|---|---|
| `sample_id`、`conversation_id`、`group_id` | 样本、会话和切分组的稳定身份；同一会话、改写及相邻截取片段归入同组 |
| `task`、`failure_tags` | 区分普通叙述、JSON现场、意图、台词草稿；标记遗忘、讨好、泄密、规则反转、传闻确证、复读等实际错误 |
| `source` | 工程提交、故事包／人物资料版本、测试报告位置、原始轮次和审核人；派生或合成资料明确标记，不伪称真人反馈 |
| `messages` | 按该模型聊天模板支持的角色组织消息；保存当轮真正可见的输入和经审核的目标回复，不把作者隐藏资料拼入NPC输入 |
| `evidence`、`known_by` | 允许使用的事实／传闻／承诺及来源、时间、知情人物；人物猜测与已确认结算分开，不能只列无来源的“正确答案” |
| `expected`、`review_status` | 必须遵守的结果、合法ID、不可泄露内容、未决条件及审核状态；未审样本不得进入正式训练集 |
| `rejected_response`、`correction_reason` | 保留原错误和修改理由，供错误分析或后续偏好训练；监督微调的正确目标只使用审核通过的回复 |

数据应覆盖跨越最近3轮的约定、角色目标与拒绝、不同人物所知差异、未说出口的内容、传闻不确定性、成功／失败／拒绝的忠实表达及结构输出。正确性依据当轮提供的证据和规则，不依据模型生成的自述。训练目标可以承认不知道，不能为了“续得顺”补出未发生的史事、交易或关系变化。

按会话和故事包／人物组切分训练、验证、测试；先固定切分，再生成改写或扩充，避免相同会话不同窗口跨集合。可从约80%／10%／10%起步，但每类关键边界都要有独立验证和测试，测试集中至少留出未训练人物、故事包及20轮以上对话。数量不足以覆盖时先补资料，不用重复同一问法凑数量。模型输出、人工改写、合成资料分别记录来源；不把未审模型回复直接回灌为正确答案。

### 4B／2080 SUPER 8 GB的训练实施要求

先确认显卡恢复及训练框架支持Turing与所选模型。推理用GGUF不直接当作通用QLoRA训练权重；按框架使用对应原始模型与分词器，记录精确版本及许可。适配器必须绑定同一基础模型，不能把旧Qwen3适配器直接装到Qwen3.5或其他候选。

第一轮采用4bit加载、LoRA、微批1、梯度累积和梯度检查点等节省显存的方式；训练精度按实际框架选择2080 SUPER支持的路线，不假定BF16或新显卡专属内核可用。序列长度先用1024～2048做少量步骤的显存与吞吐检查，再按任务所需长度调整；不承诺8GB可训练8K／16K，更不能通过截掉关键条件声称长对话已经训练。LoRA秩、目标层、学习率、累积步数和停止条件全部写入可复现配置，由小批与验证结果确定，不在本页预填“最佳参数”。

训练只对经审核的目标助手回复计算相应监督损失，检查模板、结束符和思考正文是否正确；输入及审核元数据不应误作回答目标。先以验证集选用模型，再只对固定测试集做最终比较。若恢复后仍无法在8GB完成所需长度，记录实际内存与失败条件，调整方案后重新评估，不将CPU分页或另一台设备的结果混称本机显卡通过。

纯CPU主要承担数据检查、分词长度核对、基线与量化后推理评估；本任务不默认安排本机4B全参数CPU训练。显卡不可用期间的可交付成果是数据、配置草案、错误分类和CPU测评，训练状态明确保留为待执行。
