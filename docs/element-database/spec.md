# 元素定义与内容规范 v0.1

状态：讨论草案。下文“沿用”表示既有工程约定；“建议”表示待用户确认的内容规范，不是已经部署的新 schema/API。

## 1. 定义与粒度

### 1.1 核心术语

| 术语 | 定义 | 例子 |
|---|---|---|
| 元素 | 可独立说明、检索、引用和适配的世界构成概念/模板 | 小麦、磨坊、行会、魔法契约 |
| 变体 | 保留共同概念、但机制或条件有所不同的版本选择 | 水力磨坊与风力磨坊 |
| 模板版本 | 某个元素的一份固定内容修订 | tools/某ID@3 |
| 世界采纳 | 作者把模板的精确版本与适配内容写进故事包 | 本世界允许水力磨坊，不允许蒸汽磨坊 |
| 实例 | 特定世界/分支中的具体对象 | 白河村第一磨坊 |
| 运行状态 | 实例随时间变化的数据 | 损坏、库存、归属、价格、是否被发现 |
| 规则 | 引擎明确支持、校验和执行的结构 | 已实现的奖励规则或显式依赖 |
| 断言 | 可单独核查的一句事实、设定或设计判断 | “本机构由地方官授权” |

**元素定义不等于命名解释。** 合格定义应回答：它是什么、边界在哪里、如何发挥作用、要什么条件、何时失效、影响谁、哪些结论不能从它推出。

### 1.2 建议的建条与拆分原则

- 能影响角色行动、世界生成、经济/制度因果或故事冲突，才优先建条；不为了百科完整性收集所有名词。
- 一个条目围绕一个可复用概念。不把具体人物、一个商店当前货架或某局事件日志塞进模板。
- 钢铁与铁矿石、活牛与牛肉、职业与店铺、宗教与教团实例不能因名字相近而合并。
- 仅地区称呼不同、机制相同的优先做别名；机制、权限或生产链不同的做变体或独立条目并关联。
- 同名只能触发人工去重检查，不能证明同物。不得仅靠去括号后的名称自动合并正典。
- 成套资料如姓名池、诗歌形式可以作为集合模板，但应标明集合粒度；不能把“一份集合”当作“一个人物”。

## 2. 分类：三种用途分开

沿用：每个元素**恰好一个主标签 primary**；其他均为次标签。非人知性体判定沿用主标签规范，不自行重定义种族。

1. **主标签**：作者最先怎么称呼它，如 grain、facility、profession、race。合法词表见 `tools/catalog_overlay.py`，不要任造枚举。
2. **次标签**：用途、材料、文化、地形、季节、题材等交叉检索维度。
3. **内容模块**：决定哪些字段适用。建议分为生命/族群、物品/材料、能力/技术、地点/建筑、职业/服务、组织/制度、生产/贸易、文化/知识、事件模板；这只是文档分工，不替换既有 category 或 primary。

题材不是权限；科技/魔法档位只是粗筛门槛，不证明具备燃料、工艺、制度和成本。宗教记述不等于超自然效力实际成立。

## 3. 通用记录要求

### 3.1 现行可用字段

| 字段/结构 | 内容要求 |
|---|---|
| group / namespace + id | 稳定身份，不把显示名当外键；引用优先显式写 namespace/id |
| schema_version / version | 采集结构版本与库内容版本分开；普通内容修订不擅改 schema_version |
| name / aliases / summary | 名称、真实别名、简短检索摘要；不能用摘要代替完整定义 |
| primary / tags | 一个主标签，多次标签；overlay 派生字段按现行规范生成 |
| details | 完整七节；无法核实的内容写明未知，不拿空话填满 |
| source_ids / sources | 具体来源及其支撑范围、访问状态、权利说明 |
| review_status / detail_status | 状态如实保留，默认待审；补齐七节不自动升格 |
| evidence_grade | sourced/mixed/inferred；与内容审核状态独立 |
| related_ids / related_catalog_ids | 普通关联，不能代替 requires/conflicts |
| game / 职业/店铺等模块 | 只按对应专门规格补适用字段，不给所有元素硬塞价格与产地 |

旧题材 schema 与新七节 schema 继续通过适配器兼容。本草案不要求立即重写旧文件。

### 3.2 七节的写作合同

| 分节 | 必须回答 |
|---|---|
| definition | 它是什么、包含/不包含什么、与近似概念的区别 |
| mechanism | 输入、过程、结果的因果关系；明确现实机制或世界自选规则 |
| conditions | 自然条件、知识、材料、能源、工艺、人员、组织、时间等前提 |
| exceptions | 失效情形、反例、代价与不能推出的结论 |
| story_uses | 能给玩家什么选择、机会和后果，不保证冲突必然发生 |
| historical_scope | 地区、时代、社会位置及传播范围；原创条目写明无史实对应 |
| evidence_and_uncertainty | 哪些有证据、哪些是设计、哪些待核，以及如何补证 |

旧 schema 的 story_consequences、adaptation_limits 应保留原意；历史范围和跨题材适配边界不能因适配器改名而混成同一事实。

### 3.3 建议补充、尚未统一实现的语义信息

- **事实性质**：经验机制 / 限定历史事实 / 信仰记述 / 类型母题 / 原创设定 / 游戏平衡值。建议在关键断言级标明，不用一个 mixed 掩盖全文。
- **适用范围**：地域、时期、气候/生态、社会条件、规模、地位、传播阶段。
- **缺失原因**：未知、未采集、不适用、存在争议要区分；0 表示真实零，不能表示“不知道”。未来 JSON 字段用什么名字和值，需单独设计校验，当前先写进详情。
- **审查记录**：元素精确版本、审查人/代理、日期、核对过的断言及来源、通过/返修/未核结论。当前可用独立文档记录，不声称已有审核后台。

## 4. 按内容模块收集，不强求同一套数值

| 模块 | 建议必答 | 需要玩法时再补的量化数据 |
|---|---|---|
| 作物/动植物 | 名称范围、生态、获取、可用部位、繁殖/季节、加工和风险 | 单位面积产量、周期、食水/劳力，附条件与区间 |
| 材料/物品 | 原料与成品区分、用途、品质、保存、运输、替代品 | 克重、容量、价格单位、损耗与维护 |
| 技术/能力 | 原理、学习/制造条件、作用边界、成本、反制、失败 | 时间、消耗、作用距离、次数、冷却；只接引擎支持的规则 |
| 地点/建筑 | 功能、选址、占地、出入口、容量、配套、维护 | 面积、人数、仓储/生产能力，附规模假设 |
| 职业/服务 | 工作内容、技能/资格、工具、雇佣关系、交付物 | 工时、工资、服务计价、培训周期 |
| 组织/制度 | 成员、权力来源、决策、收入、义务、制裁、退出 | 征收/服务规则；不把某地制度推成全世界通例 |
| 生产/贸易 | 输入→加工→输出、设施、角色、运输、替代与瓶颈 | 每批数量、时间、能源、损耗、库存规则 |
| 文化/知识 | 地区时期、实践者、载体、传播、禁忌、权利 | 仅在玩法要求时增加成本或熟练条件 |
| 事件模板 | 触发条件、参与者、选项、状态变化、结束条件 | 概率、频率、数值后果须另作设计，不伪称史实 |

数值必须带单位、条件、依据和性质（测得/历史资料/估算/游戏设计），可以未知，不能伪造精确值。现实危险操作、药物剂量和诊疗处方不在本库采集目标内。

## 5. 关系与条件

### 已实现的三类关系不得混淆

- 普通关联：帮助浏览与比较，不触发执行，目标可能未解析。
- 显式 requires：清单选择依赖；不是“已经满足制造条件”。选了煤和蒸汽机不等于本地已有煤库存、锅炉工厂与技工。
- 显式 conflicts：选入冲突；自然语言条件仍需作者判断。

### 建议采集的关系词表（尚非可执行 schema）

| 关系 | 例子 |
|---|---|
| 原料/产物 inputs / outputs | 铁矿石→冶炼工艺→铁料 |
| 需要设施/技能 requires_facility / requires_skill | 锻造需要锻炉与金工技能 |
| 提供服务 provides_service | 铁匠铺提供修理服务 |
| 替代品 substitutes | 动物牵引可替代部分人力 |
| 变体 variant_of | 风力磨坊与磨坊概念关联 |
| 加工自 derived_from | 牛肉来自家牛，不是牛的同义词 |
| 社会关系 governed_by / grants | 行会规章约束准入、资格授予执业许可 |
| 生态/空间适用 suitable_for | 作物适用特定气候、土壤和生产用地 |

每条建议关系记录两端身份、方向、适用条件、证据/设计性质。数量关系另记单位和时间基准。生态共存等关系可成环，不能把所有关系一概塞进要求无环的 requires 图。

## 6. 单位、价格与地图（沿用既有决定）

- 物品重量存整数克；长度与容量用公制。货币存整数铜币，10铜=1银、10银=1金。详见 `docs/units.md`。
- 商品价格是附背景的游戏基准，不是全世界恒定行情；实际成交价与库存属于旅程状态。
- 后续量化生产必须区分存量、每批产量、每单位时间流量，不能只有一个“数量”。
- 地图条件通过现有消费契约映射；当前默认 `world_map_product`（Terragenesis），civ-atlas 为可选后端，见 [地图策略](../map-backends.md)。资源适生、建筑选址、商路和势力条件按实际图层与尺度适配，缺项列明。
- 元素模板存“适用什么条件”；具体世界/分支/版本/entity或cell的位置映射放在实例层。
- 森林不等于有某种树；矿物存在不等于可开采矿床；适合耕作不等于已有农田；河流 flux 不等于可用水库存。

## 7. 世界绑定、可见性与规则

沿用三层隔离：**全局模板 → 故事包采纳快照 → 世界/旅程实例**。

- 开局固定明确版本、必要详情、来源记录和允许的潜在元素；潜在不等于已制造、已普及或角色已知。
- 库更新不能改写旧故事包。中途新增未绑定类型须作者新版本/新旅程或显式分支，不静默补库。
- 作者审核、世界采纳、角色知情是三个独立维度。
- 公开信息沿用 disclosure 白名单和受众条件；作者内部全文、来源和秘密不能默认全部给玩家。
- 任意脚本、eval 或百科中的公式不直接成为可执行规则。具体规则接入另有经过校验的受支持合同。
- 当前装配有16元素等V1工程上限，不是内容规范认为世界只能有16种事物；是否扩容需另立实现任务。

## 8. 采集、审查与验收

流程建议：确认范围 → 查重/复用 → 收集定义与条件 → 记录来源 → 形成候选 → 结构校验 → 内容审查 → 作者适配 → 版本固定 → 实例化。

最低验收：
1. ID稳定、字段与七节有效、引用可解析；新分区显式登记，不通配混入。
2. 定义有边界；条件、例外和跨字段不自相矛盾；不同事实性质不混写。
3. `access=read` 只有实际读到正文时使用；读到部分就限定支撑范围。链接和搜索摘要不能证明全文。
4. 对历史年代、地域制度、技术性能、健康等关键断言逐项核对；记录未核内容。抽样通过不代表全库通过。
5. 纯原创允许无外部来源，但须明写原创、自选机制、限制与反例，不能假造史实背书。
6. 许可与事实可信度分开：可阅读不等于可复制。保存来源、权利说明与转述/改编范围。
7. 沿用现行升格权限：采集代理保持候选；需主审逐条实质核验才可改为 reviewed_detail。新审核记录方案需另行实现，不用导入成功充当审核。

**规范确认前不改变旧schema、不批量提升状态、不覆盖旧版本。**
