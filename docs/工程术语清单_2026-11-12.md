## 1. 世界内容与包

依据：[当前领域定义](../CONTEXT.md)、[故事包定义](story-package-definition.md)、[背景流程](world-background-pipeline.md)、[内容存储](../app/background_package.py)、[旧包运行](../app/runtime.py)。

| 当前词 / 标识 | 实际含义或问题 | 建议用法 |
|---|---|---|
| 故事包 / StoryPackage | 包括地图和基于地图的世界历史；历史上也用于指旧可玩内容 | 保留总概念；国家、种族等社会内容归入世界历史，文件类型另写背景包或可玩包 |
| 世界背景包 / 背景包 / `background` | 当前独立发布的背景内容 | 统一简称“背景包”，首次写“世界背景包” |
| 运行包 / 可玩包 / `story.json` | 包含开局及可执行内容的旧包 | 日常说明统一“可玩包” |
| 世界观 / `worldview` | 旧模块的总概与世界规则文字 | 原模块名保留；介绍完整内容时写“世界背景” |
| 宏观世界背景 / 世界背景 | 世界和国家层面的背景 | 一般说明统一“世界背景” |
| 世界历史 | 基于地图的史事，以及国家、种族、制度、文化和群体关系的形成、演变及背景年份状况 | 保留；不能只理解为事件年表 |
| 世界设定 / `setting` | 有时指所有设定，有时只指题材科技魔法选项 | 选项组写“题材与档位”；已采用内容写“世界设定” |
| 元素数据库 / 百科 / 候选库 / ELEMENT CODEX | 跨世界复用的设定和参考资料 | 作者正文写“设定资料库”；旧模块名作为查找别名 |
| 元素 / `element` | 可复用模板，不是世界中某一个具体对象 | 作者正文写“资料条目” |
| 实例 / 模板 | 某一具体人物或地点 / 可以复用的定义 | 首次解释，开发设计中保留区别 |
| 元素装配 / `element_assembly` | 选择资料、固定版本并关联世界 | 写“选择世界采用的资料” |
| 元素清单 / manifest / 采用清单 | 本世界采用的条目及版本记录 | 写“采用清单”；manifest 按内容另作解释 |
| 元素快照 / `element_manifest` | 包含原文、版本和来源的固定副本 | 写“采用资料的固定副本” |
| 种族 / race | 世界中的种族设定 | 保留；不把资料模板自动解释为已有当地居民 |
| 势力 / faction | 组织、集团或政治力量 | 保留，与国家及人物关系分开 |
| 聚落 / settlement | 城市、城镇、村落等统称 | 功能入口用“城镇”；列明范围时可写“城镇与村落” |
| 角色包 / character package | 独立保存的角色内容 | 保留；不能与 NPC 角色卡混用 |
| 知识点 / knowledge | 背景资料文档或玩家获得的信息，所处位置不同 | 分别写“背景资料”“旅程笔记”，旧目录名保留 |

## 2. 创作操作与版本

依据：[背景存储](../app/background_package.py)、[旧世界流程](../app/world_package_pipeline.py)、[历史存储](../app/world_history_store.py)、[城镇存储](../app/towns_store.py)。

| 当前词 / 标识 | 实际含义或问题 | 建议用法 |
|---|---|---|
| 候选 / candidate | 待选择或待审的内容 | 保留；说明是库资料还是生成草稿 |
| 草稿 / draft | 可继续编辑的内容 | 保留 |
| 选择 / select | 当前选取的内容 | 保留，不代表已写入世界 |
| 采纳 / adopt / 采用 | 纳入指定世界；旧功能有不同提交行为 | 新文案统一“采用”，保留原接口和操作效果 |
| 审阅 / 审核 / review | 人检查内容并作决定 | 操作统一“审核”，阅读动作可写“查看” |
| 批准 / approve | 同意候选或一条扩充 | 写清“确认新增史事”或“确认采用”，不要一概当成发布 |
| 确认 / confirm | 不同接口分别负责发布、同意操作等 | 按结果命名，不用孤立的“确认”解释整项功能 |
| 发布 / publish | 形成可供后续读取的版本 | 保留；不表示上传互联网 |
| 启用 / activate | 改变新旅程默认使用的可玩包 | 写“启用可玩包” |
| 锁定 / 冻结 / pin | 后续继续引用确定的版本 | 写“固定版本” |
| 不可变版本 / immutable | 已发布版本保留，修订形成新版本 | 写出这个行为，开发文档保留术语 |
| 修订 / revision | 编辑计数或内容版本，模块间用法不同 | 编辑检查写“修订号”，发布内容写“版本” |
| version_id / schema_version / rules_version | 内容、数据格式、结算规则的不同版本 | 分别标注对象，不能统一替换字段 |
| 过期 / stale / freshness | 来源变化或编辑所依据的修订号落后 | 写明“地图来源已变化”或“内容已被修改” |
| 上游 / 下游 | 前后阶段依赖 | 作者界面写“修改此阶段后，后续阶段需要重新生成” |
| 失效 / 悬空引用 | 结果不再适用 / 关联对象不存在 | 分别写清需要重做的阶段或缺少的对象 |
| 回滚 / rollback | 恢复到已有保存记录 | 玩家说明写“恢复到指定记录” |
| 回放 / replay | 重新执行或查看历史过程 | 保留区别；不能代指恢复存档 |

## 3. 历史、国家与疆域

依据：[文明模拟](civ-sim.md)、[背景地理](../app/background_geography.py)、[模拟引擎](../app/civ_sim/engine.py)、[背景生成](../app/background_package.py)。

| 当前词 / 标识 | 实际含义或问题 | 建议用法 |
|---|---|---|
| 文明模拟 / civ_sim | 按规则计算政治实体、扩张和历史等 | 保留；首次可补“模拟国家形成与历史变化” |
| 历史骨架 | 模拟已经确定的史事和身份关系 | 写“模拟史事”或“已确定的历史” |
| 编年史 / chronicle / annals | 按年保存的模拟记录 / 其中的事件表 | 作者界面写“模拟历史”；详细结构中保留原名 |
| 史事 / event | 世界历史中的建国、战争、继承等 | 统一“史事”，与游玩事件区分 |
| 重大扩充 / major_history_proposals | AI 建议新增、需作者确认的重大史事 | 写“待确认新增史事” |
| 政体 / polity / polities | 代码常指政治实体，中文又常指君主制等制度 | 国家对象写“国家”；制度形式才写“政体” |
| 王国 / kingdom | 当前背景模块的国家称谓 | 保留当前功能用语；不是制度模拟结果的证明 |
| 王朝 / dynasty | 统治家族或连续统治时期 | 保留，与国家身份分开 |
| 国祀 / faith | 模拟记录的国家信仰等；外来数据也可能是普通宗教 | 按来源写“国家信仰”或“宗教”，不机械合并 |
| 背景年 / background_year | 这份背景描述的历史年份 | 首次写“背景年份” |
| 存续 / alive / ended | 指定年份是否仍存在 | 界面写“仍存在 / 已灭亡”；人物则写“在世 / 已死亡” |
| 州 / province / region | 本地模拟中用于计算归属的粗分区；外部 region 还可能是选定地区 | 本地写“模拟分区”，来源地区仍写“地区” |
| 州尺度代理疆域 | 分区归属裁剪到陆地得到的近似范围 | 写“按模拟分区估计的疆域”，并保留精度限制 |
| 首都州 / capital_region_id | 首都所在的模拟分区 | 写“首都所在分区”，不能改称精确城址 |
| 连接边 / adjacency / roads（模拟内部） | 分区连通关系 | 写“分区连接关系”，不当成已生成道路 |
| 陆块 / landmass | 按陆地连通关系得到的范围 | 首次写“连通陆地”，随后可用陆块 |
| 大陆 / continent | 地理称谓与人文分类 | 保留；不把每一个连通岛屿称为大陆 |
| 文明偏好 / 政体偏好 / profiles | 河流、海岸、高地、距离的四项权重及依据 | 写“国家选址与扩张偏好”，不暗示已模拟种族全部特性 |

## 4. 游玩、人物与信息

依据：[检定规则](check-system-v2.md)、[任务](quests-contract.md)、[事件](events-contract.md)、[角色卡](npc-character-cards.md)、[游玩建议](综合游玩建议_2026-11-12.md)、[存储](../app/storage.py)。规划用语不代表已实现。

| 当前词 / 标识 | 实际含义或问题 | 建议用法 |
|---|---|---|
| 表层 / surface | 玩家可见界面或返回给玩家的数据 | 说明中写“玩家界面 / 玩家可见信息”，按上下文区分 |
| 里层 / inner | 作者编辑及调试区域 | 说明中写“作者界面” |
| 旅程 / session | 持续的游玩过程及状态 | 保留“旅程”，不要一会儿称聊天一会儿称会话 |
| 回合 / turn | 一次提交、规则结算和结果叙述 | 保留；不自动等于固定一小时 |
| 事件 / event | 游玩中的场景、节点及行动安排 | 保留“事件”；说明历史记录时改用史事 |
| 事件池 / event pool | 可供规则选择的事件集合 | 开发中保留，普通说明写“可发生的事件” |
| 任务 / quest | 可接受、进行、提交或终止的目标 | 保留，与事件分开 |
| 动作 / 行动 / action | 玩家选择或规则支持的一次行为 | 玩家文案统一“行动”；代码和规则名保留 |
| 检定 / check | 根据能力、条件和规则计算行动结果 | 保留；可解释为“行动能否成功的规则计算” |
| 判定 / 裁定 / judgment | 场景、意图或可行动性的判断 | 说明具体判断对象，不当作检定的随意别名 |
| d20 | 20 面骰规则中的骰子 | 首次写“20 面骰（d20）” |
| DC | 检定需要达到的数值 | 界面写“难度”，规则说明写“目标值（DC）” |
| mod / factors | 属性或条件带来的修正 | 界面写“能力修正 / 有利和不利条件” |
| advantage / disadvantage | 按规则掷两颗骰取高 / 低等 | 保留“优势 / 劣势”，不要解释成任意属性加分 |
| position / effect / tier | 行动处境、效果程度、结果档位 | 面向玩家写“风险 / 效果 / 结果”，具体规则仍按配置解释 |
| 加码 / push | 承担额外代价来提高机会 | 首次解释代价，保留规则名 |
| 进度钟 / 危险钟 / clock | 分格记录进展或危险积累，不是钟表时间 | 界面写“进度 / 危险积累”；技术规则中保留 clock |
| 压力 / pressure | 随时间推进的局势变化；角色卡里也指个人牵制 | 分别写“局势变化”“人物困境”，避免与情绪压力混同 |
| flag / 标记 | 记录条件是否成立的状态 | 开发中保留“状态标记”，玩家显示实际变化 |
| reward / resource / inventory | 奖励、可增减资源、物品清单 | 各保留具体名称，不全称“资源” |
| NPC / 非玩家角色 / 次要角色 | 不是由玩家直接扮演的人物；不一定是次要人物 | 首次写“非玩家角色（NPC）”，后文可写“人物” |
| 角色卡 / npc_card | 人物经历、价值观、目标、底线和知识记录 | 保留；不等于独立角色包 |
| 事实 / facts | 世界中已成立的情况 | 保留，不从叙述或传闻直接提升为事实 |
| 信念 / beliefs | 角色相信的内容，可能错误 | 普通说明写“角色认知”，接口原名保留 |
| 所闻 / heard | 玩家已获得的信息，未必真实 | 写“玩家所闻” |
| 公开字段 / public_fields | 作者允许展示、仍要按可见条件筛选的字段 | 写“允许公开的信息”；详细编辑显示字段名 |
| 确信程度 / confidence | 角色相信某项认知的程度 | 保留，不改称事实正确率 |
| 注意 / 猜测 / 第一印象 | 用户确定的玩法方向：辅助观察、推断及人物初始判断 | 日常词足够，不再另造体验层或心理子系统名称；仍属规划 |

## 5. 地图、气候与水文

依据：[地图数据要求](world-map-source-contract.md)、[地图说明](world-map-integration-handoff-20261111.md)、[算法分工](terrain-algorithm-map.md)、[地图界面](../app/static/map-bundle.js)、[地图读取](../app/map_bundle.py)。保留必要学科词，简化展示方式。

| 当前词 / 标识 | 实际含义或问题 | 建议用法 |
|---|---|---|
| TG / Terragenesis | 外部地理生成工程 | 首次用完整项目名，后文可用 TG |
| civ-atlas | 外部地图与文明项目及旧接入来源 | 保留正式名称，不与本地 `civ_sim` 混称 |
| 地图包 / map bundle | 登记的一组地图及环境来源 | 作者正文写“地图数据包” |
| 产品 / product / 产物 | 已生成并保存的数据或文件 | 按内容写“地图数据”“地形文件”“预览图” |
| 冻结产品 | 固定来源与版本的已保存数据 | 写“已保存并固定版本的地图数据” |
| 同源 / binding | 派生数据的来源关系经过核对 | 写明“使用同一份地形”或具体来源，不能只说版本号相同 |
| skeleton / 地形骨架 | 地形生成的基础结构 | 写“基础地形” |
| fast / 快速世界层 | 某项具体生成阶段和数据格式 | 写“快速地形生成阶段”；不保证所有地图都同样快 |
| TD | 本工程地形模型步骤的简称 | 普通说明写“地形模型”；参数和算法记录保留原名，不猜扩展名 |
| 原生网格 / native grid | 字段最初保存时使用的网格 | 写“原始网格”，说明各组格大小可能不同 |
| 母场 / 母网格 | 用来派生其他数据的较粗原始数据 | 写“原始粗网格数据”，需要时列实际大小 |
| 栅格 / grid | 逐格保存的空间数据 | 面向作者写“地图网格”，学科说明可保留栅格 |
| 格心 / cell centre | 地图格的中心位置 | 写“网格中心” |
| 点窗 / 格窗 / window | 单点查询和矩形区域查询的混合简称 | 分别写“查询地点”“查询矩形区域” |
| 掩膜 / 掩码 / mask | 一组标识哪些格可用或可见的数据 | 空间数据开发说明统一“掩膜”；作者界面写“陆地范围 / 可见范围”等实际对象，位运算掩码另论 |
| LAND / OCEAN / CLOSED_BELOW_SEA | 来源定义的不同地形状态 | 文案按状态解释；低于海面的封闭地区不自动视为普通陆地或海洋 |
| DEM / elevation_m | 逐格高程数据 / 海拔字段 | 界面写“海拔”，开发首次写“数字高程模型（DEM）” |
| bed / surface | 基底地形 / 表面，具体是否含冰等由来源决定 | 写清“基底海拔”“冰面海拔”等，不能都改称地面 |
| 流域 / basin / drainage area | 水流归属范围 / 汇水面积 | 保留正确学科名，分别注明面积单位 |
| routing / receiver | 水流去向 / 下一个接收水流的格 | 界面写“水流去向 / 下游网格”；与网页路由分开 |
| 拓扑 / graph / adjacency | 网格或流路的连接关系 | 普通说明写“连接关系” |
| 汇流 / runoff | 流量沿连接汇集 / 产流或径流，字段量纲可能不同 | 保留区别，不全替换成“河流” |
| Q / discharge | 流量，具体是坡面还是含湖总流量取决于字段 | 写“流量（m³/s）”，保留来源范围 |
| SWE | 雪或冰折算成液态水的深度 | 写“积雪折合水深 / 冰折合水深（mm）”，不当成实际雪厚 |
| CSR | 稀疏图的一种存储结构，用于本批地表水计算 | 仅在算法和调试详情保留；界面写具体水文功能 |
| 月均 / 月累计 / 月末存量 | 时间平均、期间累加、月末保存量 | 必须保留区别，不笼统改成“每月数据” |
| 有限首年 / noleap365 / 诊断年 | 有限范围、365 天无闰的某次模拟年 | 写“本次模拟的第 1 年（365 天）”，保留不能证明多年稳定的说明 |
| 支持域 / support / nodata | 已有有效计算的范围 / 缺测标记 | 写“有数据的范围 / 暂无数据”，不把缺测写成零 |
| 潜在湖 / 实际湿域 / 永久水域 | 候选地形范围、本次模拟有水范围、需要长期依据的判断 | 保留区别，“实际”说明是本次模拟结果，不暗示实测 |
| 矢量 / raster / 渲染 | 点线面数据 / 栅格图像 / 绘制过程 | 界面写“河流线”“底图”“生成预览图”等具体内容 |
| 投影（地图） | 空间坐标到显示坐标的变换 | 保留术语；不能套用“玩家可见信息”替代 |

## 6. AI、接口与工程维护

依据：[模型调用](../app/provider.py)、[提示输入](../app/prompts.py)、[存储](../app/storage.py)、[模块说明](模块.md)、[背景生成](../app/background_package.py)、[模型用量](token-usage-evaluation.md)。

| 当前词 / 标识 | 实际含义或问题 | 建议用法 |
|---|---|---|
| 上下文 / context | 本次送给模型的资料 | 作者设置写“发送给模型的资料”，开发文档可保留上下文 |
| 上下文预算 / context_chars | 本地字符上限，不是模型 token 上限 | 写“输入资料字符上限”，明确计量方式 |
| prompt / 提示词 | 给模型的指令 | 开发中保留提示词；作者操作写具体创作要求 |
| token（模型） | 模型统计输入输出的计量单位 | 保留 token 并首次解释；不换算成固定字数 |
| token（访问） | 本地作者访问凭据等 | 写“作者访问令牌”，与模型用量分开 |
| API Key | 模型服务的访问密钥 | 写“API 密钥”，不能与本地访问令牌混同 |
| provider / model / agent | 模型调用适配、模型、智能体三个不同对象 | 按实际写“调用适配器 / 模型 / 智能体” |
| 离线模式 / offline | 使用本地规则或编辑模板，视功能而定 | 标明“本地规则生成”或“离线编辑模板”，不声称在线模型已工作 |
| 分批输入 / batching | 多次按任务输入资料 | 保留“分批”；不能只处理首批却声称全部完成 |
| 确定性 / seed | 固定算法和输入下的相同结果 / 随机种子 | 普通说明写“相同输入与种子得到相同模拟结果”；不扩展到在线 AI 正文 |
| JSON / schema | 数据表示格式 / 字段结构要求 | 首次写“结构化数据（JSON）”“数据格式”；保留示例原键 |
| payload | 请求正文或条目原始内容，含义随位置不同 | 按对象写“提交内容”“原始条目内容”，不统一音译 |
| manifest | 地图来源清单、采用清单或资源清单 | 按用途写具体名称，文件名 `manifest.json` 保留 |
| provenance | 生成及采用依据 | 写“来源记录” |
| identity / digest / hash / SHA | 来源标识及不同校验值 | 作者写“来源标识 / 内容校验值”；具体算法保留 |
| snapshot / 快照 | 固定内容副本或某时刻状态 | 分别写“资料固定副本”“历史状态记录”“代码检查点” |
| projection / 投影（非地图） | 筛选给某类读者看的信息 | 写“玩家可见信息”或“作者预览” |
| trace / 审计 | 调用调试记录 / 规则执行记录 | 分别写“模型调用记录”“规则结算记录”，保留具体用途 |
| contract / 契约 / 合同 | 接口、数据或行为约定 | 文档标题优先写“接口约定 / 数据要求 / 规则说明” |
| pipeline / 管线 / 流水线 / 链路 | 多阶段处理过程或数据依赖 | 普通正文统一“流程”；数据关系写“数据流向” |
| 骨架 / 闭环 / 打通 | 基础内容 / 完成一系列步骤 / 功能连接 | 指明实际对象和完成步骤，不作为单独状态 |
| 落盘 / 持久化 | 保存到文件或数据库 | 面向用户写“保存” |
| 消费 / 接线 / 桥接 / 适配 | 读取、连接或转换不同模块的数据 | 用实际动作解释，开发模块名保留 |
| CAS / expected_revision | 保存前比较修订号，避免旧编辑覆盖新内容 | 作者提示写“内容已变化，请刷新后重试” |
| 幂等 / idempotent | 指定操作重复执行不会重复应用同一结果 | 说明是防止重复奖励、重复发布等哪一种行为 |
| 原子 / transaction / 事务 | 同一组操作的成功失败边界 | 普通说明写“一起成功，失败时一起撤销”，数据库设计保留事务 |
| 白名单 / whitelist | 明确允许的字段或操作 | 写“允许的字段 / 操作清单” |
| 缓存 / cache | 可重用的读取或计算结果 | 保留；不把它当唯一存档或原始数据 |
| 侧车 / sidecar | 关联在主数据旁的补充文件 | 写“附加数据文件”，按内容注明气候等 |
| 旁路 / 宿主 / shim | 独立实现、承载外部界面的程序、兼容旧入口的代码 | 写“独立实现 / 地图运行组件 / 兼容入口”，按实际含义解释 |
| 回归 / 冒烟 / 集成测试 | 旧功能检查 / 基本可用检查 / 多模块联合检查 | 报告写明检查范围；开发测试类别保留 |
| 验收 / evidence / 证据 | 对要求的实际核对及支持记录 | 写具体测试、运行条件和结果，不笼统代表全工程完成 |
| checkpoint / commit / push | 检查点、本地代码提交、远端上传 | 分别写清是否已上传及核对远端 |
