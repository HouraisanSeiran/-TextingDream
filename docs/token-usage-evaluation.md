# 模型接入后的 token 消耗评估

> 2026-10-31 核对：本页下述“单次请求观测值”表述不准确。当前实现会把单次请求按 1 秒外推每小时，且统计窗口只过滤记录；usage 部分缺失等口径也待修。当前仅完成观测入口，未完成可信的消耗速率评估。请以工程根 `工程交接与工作进度_2026-10-31.md` 第 6 节为后续工作依据。

当前工程已经在每次模型请求的 trace 中保存供应商返回的 `usage`，包括 `prompt_tokens`、`completion_tokens`，以及 DeepSeek 返回时的缓存命中/未命中信息。新增的 `/api/inner/token-usage?hours=24` 和「模型输入输出」页统计这些记录。

统计口径：

- 输入 token 和输出 token 分开统计；合计为二者相加。
- `token/小时` 使用统计窗口内最早和最晚观测请求的时间跨度计算。只有一个请求时，它只是该请求的观测值，不是长期平均。
- 供应商没有返回 `usage` 的请求（包括离线模拟）标为未知，不计为 0。
- 缓存命中只改变可计费/可计算的输入部分，不会减少模型输出 token；命中率没有返回时显示未知。
- trace 只保留最近 200 次，因此这是“最近保留记录”的速率，不是完整账单。

按当前请求链估算，单轮表层对话通常包含固定系统前缀、动态场景上下文和玩家输入；历史轮数、检索知识、NPC 卡和元素清单会增加输入 token。`context_chars` 是字符上限，不是 token 上限，实际 token 必须以供应商 `usage` 为准。开启推理模式时，部分供应商会把推理计入输出或单独字段，工程不把缺失字段猜成 0。

运行本地统计，不会访问模型：

```powershell
D:\anaconda\python.exe -X utf8 tools\token_usage_report.py --db data\textiledream.sqlite3 --hours 24
```

浏览器入口：左侧「模型输入输出」。选择 1 小时、24 小时或 7 天，查看调用次数、已计量次数、输入/输出 token 和 token/小时。`/api/inner/token-usage` 使用现有作者 token 和本机访问限制。

## 对消耗的直接控制点

1. 表层请求保持固定前缀，动态资料放在末尾，便于供应商缓存命中。
2. 文化资料和姓名池只在元素装配时选入故事，不把整个百科库注入 prompt。
3. 运行时检索只投影命中的知识点；角色卡、记忆和历史仍受现有上下文预算裁剪。
4. 输出预算 `max_tokens` 是上限，不是每轮必然消耗；需要结合 trace 的 `completion_tokens` 判断。
5. 接入新模型后先观察 20–50 个成功请求，再用输入、输出和缓存字段评估速率；不要用字符数直接换算账单。

可复现测试：`python -m pytest tests/test_token_usage.py tests/test_prompt_cache.py -q`。
