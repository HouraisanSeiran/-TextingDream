# 模型接入后的 token 消耗评估

2026-11-13 按当前代码修订。输出预算与单位见[模型输出规范](模型输出规范.md)，本地模型真实对话验收见[测试说明](本地模型对话测试.md)。本页描述已记录用量的统计方式，不提供模型速度或费用实测结论。

当前工程保存供应商返回的 `usage`，包括 `prompt_tokens`、`completion_tokens`及服务提供时的缓存命中／未命中信息。[存储层](../app/storage.py)将用量另存为 `model_usage`，与调试正文分开。`/api/inner/token-usage?hours=24` 和「模型输入输出」页读取这些用量记录。

统计口径：

- 输入token和输出token分别统计已报告的非负整数；任一请求缺少其中一项时，不能得到完整合计，`total_tokens`为未知。输入、输出各自的部分已知小计仍可展示。
- `token/小时`按所选窗口时长计算，例如24小时内的已报告用量除以24；没有明确窗口时速率未知。它不按首尾请求间隔计算，也不把单请求按1秒外推。
- 供应商没有返回用量时标为未知，不计为0；离线模拟和未发送的阻止记录分别统计，不计入已发送调用数。
- 缓存命中只改变可计费/可计算的输入部分，不会减少模型输出 token；命中率没有返回时显示未知。
- 调试trace正文保留最近200条，用量独立保留90天；清理正文不代表用量随之清空。返回的 `coverage.complete_since` 和 `window_complete`标明覆盖范围；启动前已丢失的历史不能重建。
- 缺失用量、覆盖不足和失败请求的计量都需单独查看，不能把部分已知小计当作完整供应商账单。详细算法见[token_usage.py](../app/token_usage.py)。

按当前请求链估算，单轮表层对话通常包含固定系统前缀、动态场景上下文和玩家输入；历史轮数、检索知识、NPC 卡和采用清单会增加输入 token。`context_chars` 是字符上限，不是 token 上限，实际 token 必须以供应商 `usage` 为准。开启推理模式时，部分供应商会把推理计入输出或单独字段，工程不把缺失字段猜成 0。

运行本地统计，不会访问模型：

```powershell
& ./.venv/Scripts/python.exe -X utf8 tools/token_usage_report.py --db saves/textiledream.sqlite3 --hours 24
```

浏览器入口：左侧「模型输入输出」。选择 1 小时、24 小时或 7 天，查看调用次数、已计量次数、输入/输出 token 和 token/小时。`/api/inner/token-usage` 使用现有作者 token 和本机访问限制。

## 对消耗的直接控制点

1. 表层请求保持固定前缀，动态资料放在末尾，便于供应商缓存命中。
2. 文化资料和姓名池只在资料选择时选入故事，不把整个百科库注入 prompt。
3. 运行时检索只投影命中的知识点；角色卡、记忆和历史仍受现有上下文预算裁剪。
4. [集中输出预算](模型输出规范.md)是上限，不是每轮必然消耗；结合服务返回的 `completion_tokens`判断，不能用请求上限填实际用量。
5. 接入新模型后观察20～50次请求，同时保留失败、截断和缺失计量；用输入、输出和缓存字段评估，不用字符数直接换算账单。

可复现测试：`python -m pytest tests/test_token_usage.py tests/test_prompt_cache.py -q`。
