# 本地专家模型候选核对

核对日期：2026-11-13。用途：为织梦选择文本生成模型提供来源与筛选依据。条件按 Ryzen 7 7735HS、约 16 GB 系统内存，以及恢复可用后的 RTX 2080 SUPER 8 GB 显存分别考虑。本轮未下载权重、未运行模型、未训练，也没有启用显卡。

本轮直接访问 Hugging Face 与 GitHub 原始文件失败，成功读取了 ModelScope 上发布者同名官方账号的模型卡、配置和文件清单。下面标注的是实际读到的来源；没有据此保证它们与另一站点此刻逐字节一致。候选的速度与质量尚未在本机测量。

## 1. 推荐顺序

| 目的 | 优先候选 | 理由及限制 |
|---|---|---|
| 希望试用每次只激活部分参数的模型 | **LFM2.5-8B-A1B，Q4_K_M** | 8.3B 总参数、1.5B 激活，支持中文；官方提供 GGUF 与 llama.cpp 用法。约 4.80 GiB 文件，适合进入 8 GB 显存／16 GB 内存候选名单。是推理模型，需检查最终正文与思考内容的分离 |
| 希望偏重格式、工具调用及许可清晰的 MoE 对照 | **Granite 4.0 H-Tiny，Q4_K_M** | 7B 总参数、1B 激活，官方中文支持、Apache 2.0，约 3.94 GiB 文件。中文叙述及本机 llama.cpp 版本兼容性需验证，不能由企业任务成绩推定文学质量 |
| 显卡暂不可用，先找低内存 CPU 对照 | **LFM3-1.7B，Q4_K_M** | 约 1.02 GiB 文件，支持中文，官方提供 CPU/GPU 的 GGUF 路径；它是稠密混合架构，**不是 MoE**。需要支持 LFM3 的新运行程序 |
| 研究开放训练流程 | OLMoE-1B-7B-0125-Instruct | 7B 总／1B 激活、Apache 2.0；官方明确英语为主，配置上下文 4096，因此不列为中文故事背景生成的首选 |

这份优先级表示值得测试的次序，不能写成“已胜过现有 Qwen3”。选择应同时比较中文一致性、合法 JSON、引用准确性、首字等待、生成速度、峰值内存与总回答耗时。

## 2. 每次激活少，不等于只存那部分参数

MoE 由路由器为每个 token 选择部分专家，降低部分计算量。不同 token 可选择不同专家，因此通常仍需要保存并读取完整模型权重；共享层、注意力、嵌入、缓存和运行时开销也不包含在“激活参数”这个数字里。

例如 LFM2.5 的 1.5B 激活参数对应的官方 Q4_K_M 文件仍有 5,155,564,768 字节，不是 1.5B 参数的文件。专家选择数量一般按模型设计使用，不能任意调小后仍声称是同一质量的模型。[S1][S2][S3]

CPU＋GPU 分担可以降低显存占用，但会受内存带宽、数据移动和运行程序实现影响。文件小于 8 GB 只说明权重有进入候选范围的条件，不证明任意上下文都能全放显存。启动时建议先测试单并发和 4096／8192 上下文，分别记录系统内存和显存，再决定是否扩大。

## 3. LFM2.5-8B-A1B：主要 MoE 候选

- **身份**：LiquidAI 的推理调优文本模型；8.3B 总参数、1.5B 激活参数。配置为 `Lfm2MoeForCausalLM`、32 个专家、每 token 选 4 个；24 层中有卷积和注意力层，前 2 层为稠密层。[S1][S2]
- **语言与长度**：模型卡列出英语、阿拉伯语、中文、法语、德语、意大利语、日语、韩语、葡萄牙语、西班牙语；上下文 128,000。这个长度是模型能力声明，不是本机推荐启动容量。[S1][S2]
- **量化文件**：官方 `Q4_K_M` 为 **5,155,564,768 字节，约 4.80 GiB**；`Q5_K_M` 约 5.62 GiB，`Q8_0` 约 8.39 GiB。8 GB 卡优先试 Q4，Q8 连完整权重本身都超过显存。[S3]
- **运行支持**：官方 GGUF 卡给出 `llama-cli -hf LiquidAI/LFM2.5-8B-A1B-GGUF` 用法；原模型卡列出 llama.cpp CPU offloading。它证明官方提供这条运行路线，未证明本机现有二进制已经支持所有模板和算子。[S1][S4]
- **许可**：LFM Open License v1.0，模型卡标 `license: other`。实际许可证将商业使用与年收入门槛关联，定义门槛为 1000 万美元；不是 Apache 2.0，部署或分发应按原许可证执行。[S5]
- **生成注意**：官方卡明确它是 reasoning model，助手回合在最终答案前含思考内容。工程要求合法 JSON 时，需要服务端正确分离思考与最终正文，并通过现有结构校验。少量激活参数不会自动减少这些额外输出的等待。[S1]
- **性能证据界限**：官方模型卡自述相对旧 LFM2 的多项成绩上升；没有织梦中文背景、人物知情范围或本机 7735HS／2080 SUPER 的测量。不要把官方其他设备的速度图填成本机 token/s。[S1]

同系列旧 **LFM2-8B-A1B** 也为 8.3B／1.5B，原卡指向本版本；新版卡又用 `new_version` 指向 LFM3-1.7B。这个字段表示发布者推荐的新入口，不表示 LFM3 仍是 MoE，也不构成全部任务质量提升的证明。[S1][S6]

## 4. Granite 4.0 H-Tiny：较小权重的 MoE 对照

- **身份与结构**：IBM 模型卡表格写明 **7B 总参数、1B 激活参数**。配置为 `GraniteMoeHybridForCausalLM`，40 层、64 个专家、每 token 选 6 个，含 Mamba2、注意力和共享专家；不是纯注意力模型。[S7][S8]
- **语言**：官方列出 12 种支持语言，包含中文；同时说明指令训练主要为英语，多语言表现未必与英语相同。只能据此列入中文候选，不能推定中文小说、制度描写或人物对话优于 Qwen。[S7]
- **长度**：配置 `max_position_embeddings=131072`；本机先按短上下文评估。[S8]
- **许可**：Apache 2.0。[S7][S9]
- **量化文件**：IBM 官方 GGUF 文件清单的 `Q4_K_M` 为 **4,230,976,352 字节，约 3.94 GiB**；Q5_K_M 约 4.61 GiB；Q8_0 约 6.88 GiB。这些是磁盘文件大小，不含 Mamba 状态、注意力缓存与运行缓冲。[S9]
- **运行支持**：确认官方发布多种 GGUF。GGUF 卡本身只注明由 IBM Granite 模型转换，本轮未取得 llama.cpp 当前源码中该架构的完整支持证据，也未实际加载本机程序。因此把“官方 GGUF 存在”与“本机已兼容”分别记录，试用前先核对 `granitemoehybrid` 的运行支持。[S9]

CPU 条件下值得与 LFM2.5 和已有 Qwen3-4B 进行相同任务测试；8 GB GPU 条件下优先测 Q4／Q5，Q8 的余量较小。以上是依据文件体积作出的筛选建议，不是运行成功记录。

## 5. LFM3-1.7B：CPU 小模型对照，不是专家模型

- **身份**：LiquidAI 官方卡称为 post-trained、text-only、1.7B 模型。配置 `model_type=lfm3`、24 层，包含短卷积、全局注意力与滑窗注意力，没有 MoE 路由与专家数量字段；不能把它写成“总量 8B、激活 1B”式模型。[S10][S11]
- **语言与长度**：官方列 16 种语言，包含中文；配置长度 262144，滑窗长度 256。[S10][S11]
- **文件**：官方 Q4_K_M 为 **1,099,627,808 字节，约 1.02 GiB**。[S12]
- **运行支持**：官方卡列 GGUF 的 llama.cpp、Ollama 与 LM Studio CPU/GPU 路线，并明确 llama.cpp 需要 LFM3-compatible build 与当前聊天模板。不能把本机已有的旧版 llama.cpp 当作已经支持。[S10]
- **输出与任务边界**：默认启用推理；官方说明 `enable_thinking=False` 的行为可能不稳定，尤其是推理任务。模型面向本地工具调用、结构化输出和专门微调，官方同时不建议用于复杂多步推理或代理编码；知识密集任务应结合检索。[S10]
- **性能证据**：官方 32K 图使用 Q4_0、GPU offload，硬件包括 Ryzen AI Max+ 395 的 Radeon 8060S Vulkan、Apple M5 Max 和 iPhone 17 Pro。它们既不是 7735HS 纯 CPU，也不是 2080 SUPER，不能直接引用图上的速度作本机估计。[S10]
- **许可**：模型卡为 LFM Open License v1.0，与前述 LFM 系列分别以实际随附 LICENSE 为准。[S10]

它适合优先测试短结果表达、意图匹配和简单结构化草稿。较小权重对 16 GB 内存设备有实际筛选价值，但本轮没有确认它在织梦任务上的质量达到现有 4B。

## 6. OLMoE：保留研究价值，中文主流程低优先级

选用 **OLMoE-1B-7B-0125-Instruct**，不是较早的 0924 版。官方基础模型说明总量 7B、激活 1B；Instruct 版经历 SFT、DPO 和 RLVR。配置为 64 专家选 8，16 层，上下文 4096。[S13][S14][S15]

许可证为 Apache 2.0；官方明确语言为 “Primarily English”。本轮未确认同版本发布者官方 Q4 GGUF 的文件大小，也未取得本机 llama.cpp 支持的证据，因此不填第三方量化文件大小或声称可直接启动。[S13][S15]

若只作容量粗筛，7B 参数全部用 4 bit 表示的理论最低载荷约 **3.26 GiB**，实际还要加分块比例、未量化张量、元数据、缓存及运行开销。这不是已存在的 GGUF 文件大小，也不是内存预测。它适合研究开源后训练流程，对中文世界历史和长背景输入并不占优先级。

## 7. 对织梦接入的下一步

1. 保留现有 Qwen3-4B 为基线；先用 LFM3-1.7B 与 LFM2.5-8B-A1B 的短任务测 CPU，Granite 作为 MoE 对照。
2. 显卡恢复后，沿用相同样本测 2080 SUPER，分别记录纯 CPU 与 GPU offload，不能混报。
3. 使用独立推理服务，通过工程现有 `/models`、`/chat/completions` 接入；单独核对聊天模板、推理内容分离、`response_format` 和输出截断。接口细节见[模型接入](model-connection.md)。
4. 每个样本统计输入 token、思考与最终输出 token（服务有报告时）、最终可用回答耗时、结构通过率和事实一致性。中文“每秒 token”不是跨分词器完全等价的文字速度。
5. 先决定可用模型与样本，再考虑 SFT／LoRA。当前训练资源按 GPU 不可用处理，本轮不做训练部署。游戏结果仍由规则计算，模型表达或提供经校验的候选。
