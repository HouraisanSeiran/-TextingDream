# 织梦的定义，以及与 SillyTavern（酒馆）生态的比对

> **历史比对（2026-11-08 整理）**：织梦一侧的依据停在 2026-11-05 及更早交接。定义和差异仍可参考，完成度见 [../现状.md](../现状.md)。

更新：2026-11-05。织梦一侧依据当时的 `README.md`、`工程交接与工作进度_2026-10-31.md`、`架构图.md` 和 `artifacts/` 下的报告；酒馆一侧依据 SillyTavern 官方文档（docs.sillytavern.app）和公开的扩展、角色卡仓库。

## 1. 定义

**织梦是一个本地运行的中文单人跑团叙事工作台。规则引擎掌握世界状态和裁决权，大语言模型只负责理解玩家意图、扮演人物和讲述；空间以 civ-atlas 生成的世界地图为基础，故事以作者编写的故事包提供。**

当前阶段：开发快照。有三个可玩短篇、两层地图移动、NPC 角色卡、四档检定和 3D 骰子，各自能运行；还没有把移动、对话、检定、钱币、结局、读档串成一条完整验收过的流程。

一句话版本：**把“主持人记账、模型讲故事”做成软件的跑团游戏雏形。**

几个容易误解的边界：

- 它不是通用聊天前端。不能导入任意角色卡就开聊，内容需要按故事包格式编写。
- 它不是开放世界模拟。自然语言行动在作者声明的行动集合里匹配，荒唐行为有后果，但不会自动生成新规则。
- 它不是纯规则游戏。没有模型时可以离线跑规则，人物对白和叙述仍依赖模型。

## 2. 比对对象

| 名称 | 是什么 |
|---|---|
| SillyTavern（酒馆）本体 | 面向 LLM 的聊天前端：角色卡、世界书（World Info / Lorebook，按关键词把条目插进提示词）、预设、正则、群聊、多 API 接入、STscript 斜杠命令脚本、第三方扩展 |
| 酒馆助手（JS-Slash-Runner 等） | 让消息楼层里运行 HTML/JS，做状态栏、交互界面等“前端卡” |
| MVU 等变量框架 | 让模型在回复中写出变量更新指令，脚本解析后改写变量，用来保存好感度、金钱、位置等状态 |
| 记忆、总结类扩展 | 自动总结聊天、把人物/地点写回世界书或向量库，缓解长对话遗忘 |
| 一批酒馆衍生前端 | 兼容酒馆卡和世界书格式的自部署 WebUI、Agent 式卡片播放器等 |

## 3. 核心差别：谁说了算

| | 酒馆 + 附庸 | 织梦 |
|---|---|---|
| 世界状态存在哪 | 聊天记录、世界书、变量（MVU）共同维护 | SQLite 里的权威状态：位置、时间、物品、钱、关系、事实 |
| 状态由谁改 | 主要是模型：MVU 下模型写出“把金钱改成 X”，脚本照做 | 引擎：玩家行动经确认后由引擎结算，模型只能提建议 |
| 检定 | 一般靠模型自行判断，或卡作者用脚本掷骰后交给模型解释 | `attribute_v1` 属性检定、四档差值，服务端出结果，骰子动画只演示这个结果 |
| 奖励与惩罚 | 模型写进正文就可能成立，靠提示词约束 | 只有引擎发放；模型不能凭空给金币或判刑 |
| 信息分层 | 世界书按关键词注入，没有原生“谁知道什么”的区分 | 客观事实 / 角色信念 / 玩家所闻三层；NPC 知识区分亲见、传闻、推测、误解，并只记同地亲见的行为 |
| 出错后 | 改聊天记录、改变量、重新生成 | 会话回滚到事件快照 |

简单说：酒馆是“模型为中心，外面加约束”；织梦是“引擎为中心，模型接在里面”。

这不等于酒馆做不到。熟练的卡作者用 MVU 加脚本，同样可以写出带状态校验和骰子的卡。区别在于这些约束是每张卡自己搭的，强度取决于作者；织梦把它们做成了所有故事包共用的底层。

## 4. 逐项对照

| 方面 | 酒馆 + 附庸 | 织梦 | 评价 |
|---|---|---|---|
| 内容格式 | 角色卡 V2/V3、世界书、预设，社区通用 | 自有故事包、NPC 卡、百科命名空间，不兼容酒馆格式 | 酒馆远强；织梦内容只能自己写 |
| 内容数量 | 社区有大量现成卡和世界书 | 3 个短篇 + 1 个三起点 Demo | 不在一个量级 |
| 地图 | 无原生地图；可用前端卡画示意图 | civ-atlas 世界地图，旅行按真实道路计时，城内街区 | 织梦的主要特色 |
| 时间与经济 | 变量里记，靠模型自觉推进 | 移动和行动推进时间；英制便士记账；时钟、阶段、截止时间 | 织梦更严格 |
| 骰子 | 扩展或脚本可掷骰 | 3D 物理骰子，结果以服务端为准 | 织梦更完整，移动端数字缺失问题待复核 |
| 长期记忆 | 总结扩展、向量库、世界书回写 | 结构化事件摘要、证据等级裁剪、确认记录优先 | 思路不同；织梦尚无大规模长对话验收 |
| 自由度 | 几乎无限，想说什么都能接 | 行动限于作者声明的集合内匹配 | 酒馆更自由，织梦更可控 |
| 模型接入 | 几乎所有主流 API 和本地后端 | 有模型适配层和离线模式，接入范围较窄 | 酒馆远强 |
| 扩展生态 | 成熟的扩展机制和大量插件 | 无插件机制 | 酒馆远强 |
| 多人 | 群聊（多角色），非多玩家 | 有协作试验产物（coop），未成形 | 都不算真正多人 |
| 成熟度 | 长期维护、用户量大 | 开发快照，接口和格式还会变 | 酒馆远强 |
| 成本 | 世界书和长上下文容易吃 token | 设计上只送当前视角需要的信息；token 统计有已知口径缺陷，尚无实测 | 织梦的优势还未被数据证明 |

## 5. 定位结论

- **酒馆适合**：和角色聊天、自由角色扮演、用现成卡快速开玩、高度自定义。
- **织梦想做的**：像跑团一样有规则、有地图、有后果的短篇冒险，世界能记住你做过什么，模型不能随口改账。
- 两者不是同一类竞争品。织梦更接近“带 LLM 叙述的跑团游戏”，酒馆是“LLM 聊天平台”。

织梦可以向酒馆生态借鉴或衔接的地方：

1. civ-atlas 本身支持导出 SillyTavern 世界书（`external/civ-atlas/README.md`），可以把织梦的世界地图资料送进酒馆。
2. 若提供酒馆角色卡到 NPC 卡的导入，可以复用社区的人物描写，但规则字段（底线、商谈条件、目击记忆）仍需作者补。
3. 酒馆在内容量、模型接入、扩展机制上的积累，是织梦短期内补不上的，不宜正面比较这几项。

## 6. 本比对的限制

- 酒馆一侧依据公开文档和仓库简介，没有逐个安装测试扩展；MVU 等框架版本众多，行为细节可能不同。
- 织梦一侧的“优势”多为设计层面，尚无真实模型 20–50 轮对话、token 成本和玩家盲测数据支撑。

## 7. 补充：酒馆里与织梦思路相近的插件（2026-11-05 查询）

依据：StatefulLore 读了 README 正文；其余只看了 GitHub 搜索摘要，未读全文、未安装测试。“状态由谁改”一栏只写摘要里能看出来的。

| 插件 | 和织梦相近的部分 | 状态由谁改 |
|---|---|---|
| StatefulLore（cgstever） | 理念最接近：“模型是写手，不是数据库”。作者写的 JS 模块持有全部状态（属性、效果、标记、计数、场景位置），每轮把权威快照注入提示词；有面板显示角色卡、物品、任务、骰子 | 代码模块（README 原话：模型什么都不记，扩展记一切） |
| Chronicle（Myrkr146） | 追踪时间、天气、钱、物品、属性、关系、地点与 NPC 名册 | 摘要原话：“模型说数值，扩展管结构”，由小型模型调用更新 |
| StatSuite（leDissolution） | 自称持久化引擎原型：记住穿着、所在房间、背包 | 摘要未说明 |
| Multihog DnD Framework | 从 RPG 状态追踪扩展成游戏引擎和模拟系统，可以用 AI 提示自建 RPG 规则 | 摘要未说明 |
| Merged World Tracker | 世界状态、会话编年、NPC 知识管理、剧情规划、NPC 内心，以及“确定性”环境条件 | 摘要只说明环境条件是确定性的 |
| RPG Map & Locations Engine | 区域→地点→房间的可导航地图，同伴同行，用物品开门，房间遭遇 | 地图与插图由 AI 生成 |
| Silly-Map、General_Map | 交互式地图 | Silly-Map 由 AI 读聊天判断位置 |
| RPG Companion、st-rpg-hud、Tracker 系列 | 状态栏：属性、任务、物品、关系 | AI 生成（st-rpg-hud 用隐藏 XML） |
| DiceSoNice | 骰子表达式 | 只出点数 |

结论：酒馆生态已有插件在做“状态不交给模型”的事，StatefulLore 最接近织梦，Chronicle 部分接近。主要差别：

1. 多数状态插件仍让模型产出数值或标签，插件负责保存和展示；织梦是玩家行动先经引擎确认、结算，模型不参与改账。StatefulLore 例外，它和织梦思路相同，区别在于规则要每个模块作者自己用 JS 写。
2. 没有查到一个插件同时覆盖：真实生成的世界地图与按道路计时的旅行、作者故事包的事件链与结局、NPC 公开/私密分层和只记亲见。这些在酒馆里要拼几个插件，彼此不保证一致。
3. 这些插件直接复用酒馆的角色卡、模型接入和社区内容，是织梦没有的。
