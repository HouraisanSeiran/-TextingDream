## 优先处理的六个问题

### 1. P1：空世界无法通过生成器创建第一个世界

位置：[element_assembly.py:1497](D:/codexwork/织梦/app/element_assembly.py:1497)，调用方为 `WorldGenerator.generate` 和 `WorldPipeline.start`。

`pin_manifest()` 无论是否显式指定元素，都先调用 `runtime.package()`。现在启动允许没有世界，但生成世界观、完整世界和启动分阶段生成也依赖这个方法，于是形成“创建世界之前必须已有世界”的循环。

**实测**：临时空库、离线模式下，`POST /api/inner/generators` 的 `worldview`、`complete` 两种请求，以及 `POST /api/inner/world-pipelines`，全部返回 HTTP 400，提示“还没有可用的世界：请先创建或采纳一个世界”。这不是供应商或 API Key 问题。原生地图开局属于另一条路径，本结论不表示所有建世界方式都不可用。

**建议**：新世界且未指定元素时允许使用空 manifest；显式引用元素或扩展现有世界时保留现有校验。增加真正从空库开始的“生成→保存→激活→新建旅程”测试，保持空世界启动的产品行为。

### 2. P1：同一开局的并发确认可以生成两个包版本

位置：[native_starts.py:435](D:/codexwork/织梦/app/native_starts.py:435)，入口 [web.py:628](D:/codexwork/织梦/app/web.py:628)。

`_claim()` 会写 `claim=True`，但不检查已有 `claim`，也不递增版本号。两个请求都能读到同一个未确认版本并成功占位。入口是同步路由，会在线程池中并发执行，且没有使用其他写包入口的 `service.lock`。

**实测**：用真实数据库和 `commit_package()`，控制两个请求在占位后交错执行；两次占位均返回 True，两个请求均返回 `created=True`，最终产生两个不同的包版本。包事务的独占日志只能阻止提交阶段重叠，不能阻止已取得错误资格的第二个请求稍后再提交。

**建议**：将占位变成带所有者的条件更新，拒绝已被占用的草稿；同时定义失败释放、进程中断恢复及重复确认返回同一结果的规则。让所有包提交入口遵守统一串行策略。补充真正并发确认和提交后重试测试，不能仅测试顺序调用两次。

### 3. P2：数据库保存成功后，派生笔记失败会把请求变成失败

位置：[runtime.py:1126](D:/codexwork/织梦/app/runtime.py:1126)。`rollback()` 和 `Service._local_action()` 也有相同保存顺序。

`finish_turn()` 先提交 `save_session()`，再写 Markdown 笔记。后一项发生文件权限、文件占用或磁盘错误时，异常会向上传播；数据库事务已经结束，无法撤销。用户看到失败后重试，可能再次推进对话或本地行动。

**实测**：注入笔记写入 `OSError` 后，`Service.turn()` 抛出异常，但存档版本从 0 增加到 1，且已经保存一轮对话。

**建议**：把数据库作为成功与否的权威；笔记作为可重建输出，失败应记录补写任务并明确返回“旅程已保存、笔记待同步”。若要求可靠补写，可在同一数据库事务中写入待办记录。增加数据库成功、文件失败、重新读取和补写的故障注入测试。

### 4. P2：部分模型请求在等待期间占用全局锁

位置：[service.py:230](D:/codexwork/织梦/app/service.py:230)，[development.py:92](D:/codexwork/织梦/app/development.py:92)，以及 `web.py` 的生成器、分阶段推进入口。

`Service.polish()` 在 `async with self.lock` 内等待供应商。角色发展建议和部分世界生成流程同样如此。这把锁还用于新建旅程、移动、关闭事件、回滚和聊天的准备/提交，因此一个慢请求会拖住这些无关操作，甚至影响另一个旅程。

**实测**：用可控的模型等待替身启动润色，另一项申请同一把锁的操作在模型返回前无法继续。本结论是锁范围验证，不是实际供应商延迟测试。

**建议**：复用 `Service.turn()` 已有的结构：短锁内读取快照和版本，释放锁后请求模型，最后短锁内校验版本再提交。不同旅程或不同草稿的协调可以逐步分开，包文件事务仍保留必要的串行限制。

### 5. P2：地图采样的同步解码阻塞异步事件循环

位置：[web.py:711](D:/codexwork/织梦/app/web.py:711)，[civ_atlas_snapshot.py:788](D:/codexwork/织梦/app/civ_atlas_snapshot.py:788)。

`map_import_sample()` 和 `map_import_town_input()` 是 `async def`，却直接调用 `_sample_record()`。后者读取整个原件、校验哈希、解析容器并重建数组，没有让出事件循环。地图导入和空间草稿转换已经使用 `run_in_threadpool`，这两个入口仍遗漏了同类处理。

**实测**：将同步读取/解码替换为可控的 150ms 工作，原本 10ms 后应执行的异步心跳约 159ms 才执行。这证明阻塞关系，不代表真实地图解码耗时为 150ms。

**建议**：将完整采样操作移至线程池，并限制同时执行的大文件任务数量。后续可按来源内容哈希加入有界解析缓存，保留文件变化检测、内存上限和失效规则。

### 6. P2：token 每小时速率的计算会严重误导

位置：[token_usage.py:23](D:/codexwork/织梦/app/token_usage.py:23)。这是工程交接文档已记录、此次再次复现的问题。

速率分母是最早与最晚 trace 的时间差，最小强制为 1 秒；选择的 `hours=24` 只控制过滤。只有一次调用时，不论实际请求或玩家节奏多长，都会按一秒外推。`calls` 还直接计算所有 trace 数量，离线记录也被纳入。

**实测**：24 小时窗口内仅一条 1000 输入 + 100 输出的记录，得到每小时 3,960,000 token、3600 次调用。现有提示却称这是“该请求的观测值”。

**建议**：分别呈现窗口内总量、每次有效调用均值、以明确窗口为分母的平均速率；不足以估计的速率返回未知。区分真实请求、离线和未发出的请求，分别报告输入/输出 usage 覆盖率。供应商 token 生成速度需要独立的耗时证据。

## 后续结构与性能改进

- **按业务拆分路由和协调逻辑。** `web.py` 1227 行、`runtime.py` 1530 行、`towns.py` 2022 行、`element_assembly.py` 1548 行。优先把旅程、世界创作、地图、配置拆为路由模块，并将包提交协调收口。目标是让锁、事务和副作用边界可检查，避免只搬文件而继续共享可变状态。
- **为长旅程减少全量工作。** `Runtime.surface()` 每轮返回完整 conversations 与 archives，包含重复的历史对话；`Store.save_session()` 每次重写会话 JSON 和三类信息层；`Recall.search()` 每次遍历历史记录并重新计算检索权重。先建立不同旅程长度的响应大小与延迟基线，再做历史分页、按版本缓存及增量索引。尚未做生产规模性能测量。
- **复用供应商 HTTP 客户端。** `Provider.complete()` 每次创建和关闭 `httpx.AsyncClient`，连接池不能跨请求复用。可由应用生命周期管理客户端，保留每次请求的配置及凭据快照、并发限制和明确关闭过程。这是优化建议，不是已测得的延迟收益。
- **保留已有可靠机制。** 会话 CAS 版本校验、SQLite 短事务、包文件事务日志、玩家/作者投影隔离都有现成实现；应扩展其覆盖范围，无需先更换数据库或重写整个后端。
