# 角色属性元素库与原有检定

六项能力沿用 `app/attributes.py`：天赋 talent、力量 strength、敏捷 agility、智慧 wisdom、社交 social、韧性 resilience，范围均为 0–100。资料命名空间为 `character-attributes`，元素 ID 与属性 ID 相同。

这六条是已有规则的可检索说明，不是新增能力或性格模板。库里记录定义，角色包记录具体数值；收录或选择元素不会覆盖人物数值。既有 Runtime 已读取角色属性并调用 `drama.resolve_check`，无需再建一套判定。

## 构库

```powershell
python -m tools.encyclopedia_build --with-traits --with-cuisine --with-attributes
python -m tools.encyclopedia_build --check --with-traits --with-cuisine --with-attributes
```

使用既有百科数据库，增量导入且重复执行幂等。旧构库开关保持原有行为；属性分区由 `--with-attributes` 显式追加。界面在元素库里可按命名空间或“敏捷”等名称检索。资料源为同目录 `character-attributes.json`，来源引用本项目实现，不伪造外部研究。

## 判定保持不变

`ability = 属性 / 100`，成功率为 `clamp(0.5 + ability - difficulty - fatigue × 0.2, 0.05, 0.95)`。运行时种子由旅程 seed、事件 ID、动作 ID 构成，同一上下文可复现；没有加入新的骰子或概率公式。

低档 <35，中档 35–<70，高档 >=70。最大血量沿用 `round(50 + 2 × 韧性)`。

能力不是性格或道德；高社交不能控制 NPC，高智慧不能读取秘密，高敏捷不代表无人目击。角色反应仍应服从其已知信息、性格、关系和地方规则。

## 复杂行为的现有限制（待用户决定）

1. 当前是单属性对固定难度、成功/失败二分。没有通用的主动对抗或多属性协同计算。
2. 没有通用的“偷取成功但被目击”等多维结果；margin 已记录，但未定义通用部分成功规则。
3. “偷取后炫耀”需要拆为有前提依赖的步骤；后一步不能在前一步失败时继续宣称持有物品。当前不能自动将任意自由文本编译成这样的规则链。
4. 性格、关系与地方规则并未统一成为目击、举报、执法和惩罚的可执行体系。现有表达提示不能代替这些状态规则。
5. 可行性必须先判：目标存在、能够接触、具备能力之后才检定。5% 的下限绝不是“不可能的事情也有机会”。
6. 固定种子意味着同事件同动作的相同条件会复现同一结果；如果允许反复尝试，要先决定重试成本和种子策略，不能静默更改现有规则。

本次只补入属性资料并验证原有接线，不替用户设计上述缺失规则，也不将它们宣称为已完成。货币和完整酒馆玩法属于后续工作。
