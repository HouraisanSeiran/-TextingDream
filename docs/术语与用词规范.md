# 术语与用词规范

日期：2026-11-12。适用于新写或修改的界面文案、工程说明、交接报告、提示词说明和代码注释。当前用词及待改位置见 [工程术语清单](工程术语清单_2026-11-12.md)；项目概念的正式定义统一放在 [CONTEXT.md](../CONTEXT.md)。

本轮建立用词规则、整理文档入口，并更新资料选择、世界设定和背景生成页的相关显示文字。接口、字段和存档格式保持兼容；清单中的其余“建议改写”表示后续修改方向。

## 1. 按读者选择说法

| 场合 | 写法 | 示例 |
|---|---|---|
| 玩家界面 | 说明玩家看到了什么、能做什么、结果是什么 | “旅程已更新，请刷新后重试。” |
| 作者界面及日常报告 | 用内容名称、操作和限制说明，不要求读者懂实现 | “修改背景年份后，需要重新模拟历史。” |
| 开发文档和调试详情 | 可以保留必要术语，首次给中文解释和对应标识 | “保存前检查修订号（CAS），防止旧页面覆盖新编辑。” |
| 接口示例、日志原文、文件路径、外部资料引用 | 保留真实名称，解释放在旁边 | `expected_revision`：本次编辑依据的修订号 |

同一段话只引入完成说明所需的名称。解释过的词不反复加括号；正常中文不强行附英文。

## 2. 内容名称

| 统一说法 | 使用范围 | 旧说法或边界 |
|---|---|---|
| 故事包 | 包括地图和基于地图的世界历史，并保留采用资料与世界条件 | 国家、种族等社会内容属于世界历史；不单指旧版事件合集 |
| 背景包 | 当前可独立保存、发布的世界背景包 | 是故事包定义的当前实现形式；说明文件类型时与可玩包区分 |
| 可玩包 | 已包含开始旅程所需地点、角色和行动等内容的包 | 说明旧功能时替代“运行包”；“启用”仍是另一个操作 |
| 世界背景 | 地图、基于地图的世界历史及采用的世界条件所构成的整体背景 | 一般说明中不再增加“宏观背景层”等别名 |
| 世界历史 | 史事与国家、种族、制度、文化等社会内容的形成、演变和背景年份状况 | 不仅是事件年表；包括群体关系和魔法对社会的影响 |
| 题材与档位 | 题材配比、科技档位、魔法档位这组选择 | 需要区分时不用笼统的“世界设定”；旧 `setting` 名称保留 |
| 设定资料库 | 面向作者介绍可复用资料时 | “元素数据库”保留为旧名称和检索别名，内部标识保持兼容 |
| 资料条目 | 库内一条可复用的资料 | 界面正文优先于“元素”；代码中的 `element` 保留 |
| 采用清单 | 本世界选中的资料条目及其版本 | 不另称“装配清单”“元素典籍”；底层 manifest 另按用途解释 |
| 城镇生成 | 依据指定背景和国家补充城镇、村落及道路 | “城镇”是功能名称，“聚落”用于明确包含村落的专业说明 |
| 玩家界面 / 作者界面 | 区分操作区域 | 日常说明优先于“表层 / 里层”；现有入口名暂保留 |
| 旅程 | 一次持续游玩的过程 | 操作存档时写“旅程存档”；`session` 在技术文档中对应旅程 |

故事包、背景包和可玩包的区别是用途与实现范围，不能仅因都放在 `StoryPackage/` 下就视为同一文件类型。

## 3. 操作名称

| 统一说法 | 含义 | 必须保留的区别 |
|---|---|---|
| 选择 | 在当前页面选中条目或选项 | 未必已经保存或计入世界 |
| 采用 | 将资料或已生成内容纳入指定世界 | 日常说明统一用“采用”；旧“采纳”是兼容别名，不改变原操作行为 |
| 审核 | 作者检查、修改并作出决定 | “资料已采用”不等于“资料已核实” |
| 确认新增史事 | 作者同意一条重大历史扩充 | 与采用库资料、发布整份背景分开 |
| 保存草稿 | 保存当前编辑，仍可修改 | 不写成“发布” |
| 发布 | 保存一份供后续读取的内容版本 | 不等于上传 GitHub、核实资料或启用可玩包 |
| 启用可玩包 | 选择新旅程默认使用的可玩内容 | 不给背景包提供该操作；已有旅程保持原绑定 |
| 创建修订草稿 | 从已发布内容开始新的编辑 | 保留旧发布版本 |
| 重新生成 | 根据当前输入重做指定阶段 | 不笼统写“刷新”；刷新页面只是重新读取 |
| 来源已变化 / 需要重新生成 | 来源变化或先前结果不再适用 | 说明对象和原因，不只写“过期”“失效” |
| 恢复到指定记录 | 向玩家说明回滚 | 开发文档保留“回滚”；与重新计算历史的“回放”分开 |
| 提交代码 / 推送代码 | Git 本地提交 / 上传远端仓库 | 与发布背景版本分开；只提交时不能说“已上传” |

## 4. 优先改写的工程行话

| 少用 | 改成什么 | 注意 |
|---|---|---|
| 管线、流水线、链路 | 流程；必要时列出步骤 | 数据经过哪些模块时写“数据流向” |
| 闭环、端到端打通 | 写明起点、终点和验证结果 | “创建、发布及重新读取均已验证” |
| 接线、消费 | 接入、调用、读取、使用 | 按实际动作选词 |
| 落盘、持久化 | 保存到文件 / 数据库 | 用户只需知道成功与否时写“已保存” |
| 投影（内容筛选） | 玩家可见信息 / 作者预览 | 地图坐标投影仍保留“投影” |
| 快照 | 固定副本 / 保存记录 / 状态记录 | 根据内容选词；详细存储设计可保留“快照” |
| 冻结 | 固定版本 / 已保存的地图数据 | 雪冰物理过程中的冻结不替换 |
| 不可变版本 | 已发布版本保留，修改时创建新版本 | 说明行为比单独解释术语更直接 |
| 身份、指纹、锚定 | 来源标识、校验值、关联或固定 | 人物身份、地理锚点保留本义 |
| 口径、粒度 | 统计方式、时间范围、计算间隔或地图格大小 | 写出具体内容，不能一律替换成“规则” |
| 骨架 | 基础地形、模拟史事、城镇基本结构 | 不把不同对象都命名为“骨架” |
| 产物 | 地图数据、背景文件、生成结果等具体名称 | 文件与内存结果的区别仍需说明 |
| 契约、合同 | 接口约定、数据格式要求、规则说明 | 现有文件名和第三方正式术语保留 |
| 幂等 | 重复执行不会重复产生同一结果或奖励 | 保留具体对象；不是“任何重试都安全” |
| 原子提交 | 一起成功，失败时一起撤销 | 不用于形容普通保存操作 |
| CAS | 保存前检查修订号 | 错误提示写“内容已被修改，请刷新后重试” |
| 白名单 | 允许的字段 / 操作清单 | 说明限制对象 |
| 回归、冒烟、验收通过 | 哪些检查通过、哪些未验证 | 开发测试名称可保留；结论必须说明范围 |

## 5. 不能为了简化而混淆的概念

1. **史事与事件**：史事属于世界历史；游玩事件包含玩家可以参与的场景和行动。二者可能关联，不能互换。
2. **事实、角色认知与玩家所闻**：世界里发生了什么、角色相信什么、玩家听到了什么分别记录。确信程度不是事实正确率。
3. **陆块与大陆**：陆块由连通陆地计算得到；大陆与岛屿的名称及人文分类由作者决定。
4. **国家、王国与政体**：国家是通称，王国是特定称谓，政体是君主制、共和制等组织形式。旧模拟的 `polity` 指政治实体，不自动证明其采用某种政体。当前背景功能沿用“王国”，不据此声称已模拟君主制度。
5. **模拟分区与行政区**：模拟用的州块只是计算范围；它不是已经设定好的行政区，也不是实际城镇。普通说明写“模拟分区”，技术位置仍可用“州”。
6. **连接关系与道路**：两个模拟分区可以相邻或连通，这不表示存在已修建道路。
7. **月均、月累计、月末存量**：温度、降水和积雪等含义不同。简化文字时仍保留单位、时间范围及缺值含义。
8. **检定与判定**：检定是按指定规则计算行动结果；判定是更广泛的判断过程。自动成功仍可属于检定，不把所有检定都解释为掷骰。
9. **版本、修订号与数据格式版本**：内容版本、编辑次数和字段结构各有用途。显示“版本”时说明对象，避免把 `revision`、`version_id`、`schema` 混为一谈。
10. **两种 token**：用量页面写“模型 token（计量单位）”；作者访问凭据写“作者访问令牌”。它们都不等于 API 密钥或字符数。

## 6. 工程命名与修改要求

- 新增界面文字先使用本规范中的中文。一个概念只有一个默认名称；新缩写只有在现有词无法表达时才引入，并在清单中解释。
- 新增代码名称优先沿用同模块已有的 `background`、`package`、`polity`、`element` 等词根。Python 沿用 `snake_case`，类名沿用 `PascalCase`，JavaScript 沿用相邻模块风格。
- 界面显示名与内部标识分开维护。现有 API 路径、JSON 键、状态值、DOM ID、数据库表、目录和环境变量保持兼容；更名需要单独安排迁移，不能用全文替换实现。
- 保留真实的第三方名、算法名和单位：Terragenesis、civ-atlas、SQLite、JSON、API、d20、m、mm、m³/s 等。首次出现难懂缩写时补短解释；默认放在开发或来源详情。
- 项目名称沿用“织梦 / TextingDream”；`TextileDream`、`TEXTILEDREAM_*`、`TEXTILE_*` 等旧标识按实际兼容用途保留。工程名后续调整另行安排。
- 单位、货币沿用 [计量单位与货币约定](units.md)。术语整理不改变数值或换算，不重写已有历史资料和人物台词。
- 日常进度写明“完成什么、怎么验证、剩下什么”。文案修改、功能实现、测试通过和线上可用分别陈述，不能互相替代。

## 7. 修改顺序与完成标准

1. **新文案立即遵循**：按钮、提示和报告优先使用统一名称，避免继续增加别名。
2. **先改常用页面**：背景生成、资料选择、城镇生成和玩家设置。只改显示文字，保持行为与标识一致，并运行对应页面检查。
3. **再改当前说明**：工程进度、模块说明、使用说明；涉及具体机制时核对代码。
4. **最后处理内部重命名**：确有维护收益时单独修改接口或存储，并验证新旧数据兼容。

每次修改核对：同一操作是否同名、近义词是否仍需区分、单位与限制是否保留、代码标识是否误改、是否把尚未实现的建议写成现状。归档、第三方源码和资料库原文保留历史名称。

## 8. 文档整理规则

- 阅读入口统一为[文档地图](文档地图.md)。逐文件目录见[现有文档总清单](现有文档总清单_2026-11-13.md)，过时判断及依据见[过时文档核对清单](过时文档核对清单_2026-11-13.md)。
- 新写或修订的说明标明用途：现行说明、兼容说明、规划草案、历史记录、资料候选或素材说明。文件日期只表示写作或核对时间，不表示业务功能已经重新验收。
- 当前进度写在工程进度中；概念定义写在 CONTEXT；接口和行为写在对应规格中。其他文档引用这些位置，避免复制出多份彼此冲突的完成度。
- 现行工程及采集说明使用“设定资料库、资料条目、采用清单、采用、可玩包、流程”。术语对照、原始资料、归档原文和代码标识按其用途保留旧词；“元素裔”等设定名称中的元素保留原义。
- 兼容文件继续说明自身适用目标，并指向新主流程。历史报告保留原数字、样本、模型和测试日期；失效的复现前提另行标注。
- 路径、链接目标、代码示例和字段名保持真实。本轮不按新显示名重命名旧文件，也不删除、移动或合并待负责人处理的文档。
