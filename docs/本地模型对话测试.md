# 本地模型对话测试

更新日期：2026-11-13。目标：确认本地模型能否承担织梦的游玩叙述与人物对话，并区分连接成功、结构合法、质量可用和等待时间可接受。

## 1. 当前判断与适用范围

**可以接入现有对话流程。** 工程支持本机免密的兼容接口、模型列表读取和真实生成请求。短对话默认输出1024 token，意图匹配256 token，见[模型输出规范](模型输出规范.md)。4B指令模型可以作为第一轮候选；模型更小或采用MoE，均不自动代表中文对话更好。

现有旅程仍以事件和场景为基础：模型接收当前人物、可知资料、近期上下文及规则结果，生成正文或结构化叙述。它不是任意建立新世界事实的通用聊天机器人。已发布的新背景包尚不能直接开旅程，不能用背景包发布成功代替对话验收。

此前旧Qwen3-4B已有两次很短的中文／JSON接口测试；这只说明短请求能够连接。**尚无本机模型通过本页完整连续对话验收的结果。** 当前显卡不可用，本轮未启动模型，未下载权重或切换正式连接。

## 2. 测试层次

| 层次 | 方法 | 可以证明什么 |
|---|---|---|
| 可移植自动回归 | 临时SQLite＋模拟HTTP | 各任务输出预算、免密本机请求、普通与JSON对话、截断不推进存档 |
| 本机模型集成 | 独立本机模型服务＋临时旅程 | 模型真实响应、JSON解析、连续回合是否完成、用量与耗时 |
| 人工质量审核 | 审阅输入／回复与对应可见资料 | 人物区分、隐私边界、规则一致性、自然程度与重复情况 |
| 性能比较 | 同一任务、单请求，分别测CPU和显卡 | 当前硬件上的实际等待时间、内存与显存需求 |

既有 `tools/local_long_dialogue_test.py` 替换了模型生成，且使用DeepSeek V3分词器估算；它是上下文组装压力测试，不能作为Qwen或其他本地模型质量、速度或准确token数的证据。

## 3. 可移植自动回归

在工程根目录运行，不需要显卡、权重、网络或API Key：

```powershell

```

`test_token_budget.py` 通过真实请求层检查发出的 `max_tokens`，验证显式覆盖与未知任务后备配置；通过真实 `Service.turn` 检查普通正文、JSON叙述及输出截断后的存档一致性。它不会证明模型自己能生成合格内容。

输出规范对作者流程也有影响，相关回归：

## 4. 本机真实请求的准备

当前可先安排CPU测试，显卡恢复后再独立测RTX 2080 SUPER 8 GB。服务与正式工程分开运行；下面命令是未来执行步骤，本轮未执行。

先以已有旧Qwen3-4B建立基准。在单独终端确认18083端口空闲后启动：

```powershell
& 'D:/llm/qwen3/runtime/llama-server.exe' `
  --model 'D:/llm/qwen3/models/Qwen3-4B-Q4_K_M.gguf' `
  --host 127.0.0.1 --port 18083 `
  --device none --n-gpu-layers 0 `
  --ctx-size 8192 --parallel 1 `
  --threads 8 --threads-batch 8 `
  --chat-template-kwargs '{"enable_thinking":false}'
```

此命令明确只用CPU；模板参数针对已有Qwen3，其他模型按各自说明配置。关闭思考和正确聊天模板对结构化结果尤其重要。若内存和响应可接受，再单独改为16384；模型标称支持更大窗口不能代替实际服务参数。新架构还需核对运行程序版本。

记录CPU、物理内存、模型精确版本与量化文件SHA-256、运行程序版本、线程、实际总窗口、模板、是否关闭思考、后台负载和并发。权重哈希可用：

```powershell
Get-FileHash -LiteralPath 'D:/llm/qwen3/models/Qwen3-4B-Q4_K_M.gguf' -Algorithm SHA256
```

## 5. 独立对话探针

[local_dialogue_probe.py](../tools/local_dialogue_probe.py)只允许本机回环地址，清空继承的API Key。它用临时SQLite、临时故事包和旅程复用现有短篇夹具，走真实 `Service.turn`；不会写正式存档、发布目录或连接设置。请求会真实使用模型算力。

先分别执行6轮结构化现场叙述与普通文本叙述：

```powershell
& ./.venv/Scripts/python.exe tools/local_dialogue_probe.py `
  --base-url http://127.0.0.1:18083/v1 --mode scene --turns 6 `
  --declared-context-tokens 8192 --context-chars 6000 `
  --output artifacts/local-dialogue/cpu-qwen3-4b-scene-6.json

& ./.venv/Scripts/python.exe tools/local_dialogue_probe.py `
  --base-url http://127.0.0.1:18083/v1 --mode plain --turns 6 `
  --declared-context-tokens 8192 --context-chars 6000 `
  --output artifacts/local-dialogue/cpu-qwen3-4b-plain-6.json
```

服务提供多个模型时用 `--model` 指定其 `/models` 中的真实ID。探针不启动或关闭模型服务；`--declared-context-tokens`只记录手动确认的服务窗口，不会自动修改或检测窗口。`--context-chars`传给工程偏好，不是所有路径都有同样的字符检查，也不会转换成token。发生窗口错误时检查报告中的请求与服务日志，调整输入／服务窗口后另存一次测试，不能以删掉失败记录计算通过率。CPU单请求超过180秒时可用 `--timeout 600`诊断；仍需按实际等待时间判断是否适合游玩。

随后将 `--turns` 改为20，使用不同报告文件名，各模式独立重复3次。脚本会循环既有测试输入，适合检查持续生成、格式和重复；它不能替代开放式人工交谈。比较不同候选时使用相同模式、轮数、窗口和模板设置，分别保留冷启动与后续运行。

报告保存逐轮输入、频道、回复、字符数、端到端耗时、服务返回用量和请求追踪；失败后停止并保存错误，返回非零退出码。`transport_and_structure_passed`只表示所有请求完成且工程校验通过，`quality_review=pending`要求另行人工审核。模型调用记录中可能包含测试人物的资料，仅使用既有测试夹具。

## 6. 人工质量与规则检查

使用已有可玩包补测下表；不需要新写剧情。每项记录输入、模型收到的可见资料、预期边界、实际回复和是否通过。不能仅因JSON合法就判定人物行为正确。

| 项目 | 测试方法 | 通过条件 |
|---|---|---|
| 正常接话 | 围绕当前目标连续追问，保留未成交条件 | 回应问题，角色立场连贯，给玩家回应空间 |
| 未说出口的内容 | 对比 `speech`、`thought`、`note`，检查实际听众 | NPC不回答未听见的内心或笔记内容，不得泄露秘密 |
| 传闻与知识范围 | 追问NPC没有亲见或只听说的事情 | 用不确定措辞，不凭空确证传闻或共享其他人的经历 |
| 规则结果 | 使用已有成功、失败、拒绝及不同档位检定 | 不反转结果，不凭空授予钱物、通行或线索 |
| 社会差异 | 比较已有不同关系、制度条件与人物卡 | 不把当地制度当成所有NPC的同一态度；衣装与行为仅按已有第一印象条件影响回应 |
| 多人和动作选择 | 指定听众，加入无法匹配或否定的意图 | 只选择合法ID或空值，不把候选当成已经执行 |
| 较长对话 | 至少20轮，跨已有场景后追问已确认事项 | 不推翻当前状态，区分不再输入的旧细节；忘记时承认不确定 |
| 表达质量 | 与另一候选盲评同样输入 | 少复读，人物有差异，遵循视角和长度要求，无思考过程混入正文 |

当前短现场叙述只提供最近3轮原始对话及少量已知信息，不保证携带与普通对话同样多的历史；某项信息没进入请求时，先记录为上下文组织限制，不能直接归咎于模型窗口太小。结构校验也不能自动发现所有叙述矛盾。连续对话风险、重要事项记忆及监督微调／LoRA顺序见[模型选型说明第8节](本地文本模型选型与使用建议_2026-11-13.md#8-微调lora-与-cnn-的位置)。

训练前应按同样的材料分别测试基础模型、改进资料输入后的模型和微调模型；记录每次遗漏信息是否实际进入请求。测试集留出未训练人物、故事包及较长对话，单独统计关键边界错误，避免只凭训练样本或输出格式判断已经完成对齐。

微调交接的工作顺序、数据字段、分组切分、2080 SUPER 8 GB实施条件与交付产物集中见[模型选型说明第11节](本地文本模型选型与使用建议_2026-11-13.md#11-交给其他智能体的本地对话微调任务)。该任务由其他智能体后续实施；本页仍只记录已有测试工具和待执行的真实模型验收。

## 7. 采用标准和记录模板

第一轮采用门槛建议如下，由负责人根据游玩节奏调整：

- 两种模式各3次20轮均完成；JSON、引用及合法反应结构全部通过；所有失败均计入报告。
- 本页规则与隐私边界专项中不出现关键错误；每项至少检查3次。自然程度单独评分，不能用速度抵消泄密或反转结算。
- 人工抽查中至少90%的回复可直接使用，修改需求有记录；这只是项目采用门槛，不是统计学上的能力保证。
- 单请求交互体验先以端到端中位数≤15秒、P95≤30秒为目标。CPU若明显超过，归为可离线创作／辅助用途，不能因能生成就认定适合即时对话。这些是建议目标，尚非本机实测。

| 记录项 | 填写内容 |
|---|---|
| 模型与运行条件 | 型号、文件SHA-256、量化、程序版本、CPU／GPU、窗口、模板、线程、并发 |
| 完整性 | 请求总数、成功数、JSON错误、截断、窗口错误、超时、重试次数 |
| 实际用量 | 输入／输出token分开，未返回时写未知；不要使用其他模型分词器冒充准确值 |
| 等待时间 | 首次请求单列、后续中位数／P95／最大值；非流式结果不提供首token时间或解码token/s |
| 资源 | 进程峰值内存、系统剩余内存；GPU恢复后单列显存峰值和是否部分退到CPU |
| 质量 | 关键错误明细、可直接使用比例、人物与文风评分、需要修改的回复 |
| 结论 | 仅连接通过／结构通过／可用于短对话／仅适合后台辅助／暂不采用 |

即使本地对话通过，也不推导长背景生成通过；背景另按来源、全部采用资料覆盖、固定历史和发布流程验收。也不能把同一地址下的 `dialogue_model`／`author_model`理解为已经支持本地与远端两个独立请求地址。
